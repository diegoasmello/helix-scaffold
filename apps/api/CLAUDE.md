# apps/api

Fastify + TypeScript — the REST API for this project.

## Stack

- **Framework**: Fastify v5 + `fastify-type-provider-zod` (validation and serialization via Zod)
- **ORM**: Drizzle ORM (pg dialect) — schema in code, migrations generated by drizzle-kit
- **Validation**: Zod (schemas declared in each module, shared between Fastify and TypeScript)
- **Auth**: better-auth (`auth.handler` integrated as a Fastify route — never use `toNodeHandler`)
- **Docs**: `@fastify/swagger` + `@scalar/fastify-api-reference` (available at `/api/docs`)
- **Tests**: Vitest + real test database (PostgreSQL)

`@/` is an alias for `apps/api/src`. Routes and services import from `@/…`; some older files still use relative paths — both work.

## Scripts

Run from `apps/api` (or from the root with the `pnpm db:*` / `pnpm spec:*` aliases):

| Script | Does |
| --- | --- |
| `pnpm dev` | `tsx watch` on `src/server.ts` with `.env` |
| `pnpm build` | `tsdown` (`tsdown.config.ts`) bundles `src/server.ts` into `dist/server.js` and `src/db/migrate.ts` into `dist/migrate.js` — `src/` only, with the `@/` alias and the PDF templates' JSX resolved; dependencies stay external (`node_modules` must be installed where it runs). `app.config.ts` is bundled, so a config change needs a rebuild |
| `pnpm start` | `node dist/server.js` (with source maps). Does **not** load `.env` — the deploy provides the environment. Does not run migrations: run `pnpm migrate` first |
| `pnpm migrate` | `node dist/migrate.js` — applies pending migrations with drizzle-orm's runtime migrator (`src/db/migrate.ts` → `run-migrations.ts`). Needs only `DATABASE_URL` from the environment: no `.env`, no `drizzle-kit`, no dev dependencies. The build copies `src/db/migrations` to `dist/migrations`. The same migrator `pnpm db:migrate` runs, and the same journal as `drizzle-kit` |
| `pnpm db:generate --name <name>` | Generate a migration from the Drizzle schema (`src/db/schema/`) into `src/db/migrations/`. **Always pass `--name`** — without it drizzle-kit picks a random one (`0017_common_husk`). The name says what changes, in snake_case: a new module's table (`news`), a change to one table `<table>_<change>` (`todos_slug`, `roles_is_admin`), one across tables the change itself (`fk_indexes`, `timestamptz`). The number prefix is added for you. A custom (hand-written) migration takes it too: `pnpm --filter api exec drizzle-kit generate --custom --name <name>` |
| `pnpm db:migrate` / `pnpm db:migrate:test` | Apply migrations to the dev DB (`.env`) / test DB (`.env.test`) with the runtime migrator (`src/db/migrate.ts`, the one `pnpm migrate` runs in production) — not `drizzle-kit migrate`, which exits 1 without printing the error when a migration fails. Same `drizzle.__drizzle_migrations` journal, so databases migrated by either work |
| `pnpm db:check` / `pnpm db:check:test` | Compares the database's `drizzle.__drizzle_migrations` with this branch's journal, by hash (`src/db/check-migrations.ts` → `migration-status.ts`). Lists the pending migrations and exits 1 on a migration the branch does not know (another branch's — its tables and enums are still there), one whose `.sql` changed after it ran, or one older than the last applied (the migrator only applies newer ones, so it would never run). `db:migrate` reports none of these: with nothing pending it succeeds, and the leftovers fail a later migration |
| `pnpm db:recreate:test` | Drops the `public` and `drizzle` schemas of the test DB and migrates it from scratch (`src/db/recreate.ts`) — the fix for what `db:check:test` reports. Refuses any database whose name does not end in `_test`/`_e2e`. The dev DB holds your data: on a mismatch there, either drop what the other branch created by hand, or `docker compose down`/remove its volume and `pnpm db:migrate` + `pnpm db:seed` |
| `pnpm db:studio` | Drizzle Studio |
| `pnpm db:seed` | Dev data (`src/db/seed.ts`). **Refuses to run if any user exists.** Wipes `uploads.dir`, creates Admin (the admin role — `isAdmin`, no permission rows)/Moderator/User roles (in open registration `User` becomes the default role, through `ensureDefaultRole()`), an admin login (`admin@example.com` / `pass1234`), 20 extra users (same password) and sample todos with uploads |
| `pnpm db:reset` | Truncates every table in the schema (`drizzle-seed` `reset`). Does not touch `uploads.dir` |
| `pnpm e2e:server` | The API of the web's E2E suite — started by `apps/web/playwright.config.ts`, which provides its environment (no `.env`). Migrates and empties the database (`src/db/migrate.ts`, `src/db/reset.ts`), then runs `src/scripts/e2e-server.ts`: `src/server.ts` with the test config plus `src/config/e2e-overrides.ts` (port 3334, uploads in `/tmp/helix-e2e-uploads`, `warn` logs) |
| `pnpm spec:export <file>` | Writes the OpenAPI spec — see _OpenAPI spec export_. After a contract change, run `pnpm spec:sync` from the repo root instead: it exports to `packages/api-client/openapi.json` and regenerates the client |
| `pnpm test` / `pnpm test:watch` | Vitest against the test DB |

`tsc` never emits (`noEmit: true`) — it only type-checks; `tsdown` produces the build. The seed and the other `src/db/*.ts` scripts are not part of the build: they run through `tsx`.

**Background jobs** start in `src/server.ts` after `listen` (not in `buildApp`, so tests never run them): orphan upload cleanup (every `uploads.orphanCleanup.intervalHours`) and, when subscriptions are enabled, subscription expiration (at startup and every `subscriptions.expiration.intervalHours`).

## Application config

Configuration is split by one rule: **secrets and per-deploy values go in `.env`; product decisions go in `src/app.config.ts`.**

### `src/app.config.ts` — product settings

The file a developer edits to shape the app. Written with `defineConfig()` (Vite-style): a plain object or a function receiving `{ mode }` (the `NODE_ENV`). Every field is optional and documented via JSDoc on hover.

| Key | Default | Notes |
| --- | --- | --- |
| `app.name` | `'Helix API'` | Title of the API docs (`/api/docs`) |
| `server.port` / `server.host` | `3333` / `'0.0.0.0'` | |
| `server.trustProxy` | `false` | Fastify's `trustProxy`: which proxies to believe for the client IP (`request.ip`). The `/auth/*` route overwrites `X-Forwarded-For` with `request.ip` before handing the request to better-auth (`advanced.ipAddress.ipAddressHeaders` in `src/auth.ts`), so its sign-in rate limit and session IPs — and the audit log's `ip` — can't be spoofed by a client header. Behind a reverse proxy set the hop count (`1`) or the proxy's IPs, or every client shares the proxy's IP (and one rate limit). Tested in `src/auth.test.ts` → _client IP_ |
| `registration.mode` | `'closed'` | `'open'` enables public self-registration. See `src/modules/registration/CLAUDE.md`. |
| `auth.socialProviders.{google,facebook,apple}.enabled` | `false` | Requires the provider's `CLIENT_ID`/`CLIENT_SECRET` in `.env`; startup fails otherwise. `apple.appBundleId` is optional (native iOS). |
| `subscriptions.enabled` | `false` | Activates the subscription infrastructure (routes, hooks, trial auto-start). See `src/modules/subscriptions/CLAUDE.md`. |
| `subscriptions.plans` | `[]` | Plan catalog: `{ id, name, features }[]`. Required (non-empty) when enabled. `features` are the keys checked by `requireSubscription('<feature>')`. |
| `subscriptions.pastDueGraceDays` | `0` | Days a `past_due` subscription keeps access, counted from `pastDueSince`. `0` = cut on payment failure. |
| `subscriptions.expiration.intervalHours` | `1` | How often lapsed scaffold-owned subscriptions (no `externalId`) are marked `expired` (`server.ts`). |
| `subscriptions.trial` | `false` | `{ days, planId }` — auto-creates a trialing subscription on self-registration (requires `registration.mode: 'open'` and `subscriptions.enabled: true`; a warning is logged otherwise). |
| `email.from` | `'noreply@localhost'` | Sender address. Must be from a domain verified in Resend for production. |
| `uploads.storage` | `'local'` | `'s3'` stub exists but throws |
| `uploads.dir` | `'./storage'` | Local storage root directory |
| `uploads.maxSizeMb` | `50` | Enforced by `@fastify/multipart` |
| `uploads.orphanCleanup.intervalHours` / `graceHours` | `6` / `24` | Orphan upload cleanup schedule (`server.ts`) |
| `logger.level` / `logger.pretty` | `'info'` / `false` | The scaffold sets `pretty: mode !== 'production'` |

**Modules receive the config, they never import it.** `buildApp(database, { config })` (default: `config` from `@/config`) hands it to every route plugin through its options (`{ database, config, … }`) and to the factories that need it (`createAuth(database, emailProvider, config, logger)`, `createRequireSubscription(database, config)`, `createEntitlementsService(database, config.subscriptions)`). Pure helpers take the slice they read (`getUsableSocialProviders(config)`, `isKnownPlan(config.subscriptions.plans, id)`). Only the entry points import `config`: `server.ts`, `src/db/seed.ts`, `src/scripts/export-spec.ts` (through `buildApp`'s default) and the test helpers. That is what lets one test file run the app in several modes.

**Adding a setting:** add the field with JSDoc to `AppConfig`, the matching entry (with `.default()`) to `appConfigSchema`, then the value to `app.config.ts`. Keep the two shapes in sync — a key missing from the schema is rejected at startup.

### `.env` — secrets and per-deploy values

Validated with Zod in `src/env.ts` at startup. If a required variable is missing or invalid, the process fails immediately with a clear message.

| Variable | Notes |
| --- | --- |
| `NODE_ENV` | `development` \| `production` \| `test`. Passed to `app.config.ts` as `mode`. |
| `DATABASE_URL`, `AUTH_SECRET` | Required |
| `BASE_URL` | Public URL of this API. Also prefixes public upload URLs. |
| `CLIENT_URL` | Public URL of the frontend (CORS, trusted origins, email links) |
| `RESEND_API_KEY` | Required with `NODE_ENV=production` (the API refuses to start without it — the console fallback would print reset links to the logs). Omit in development to fall back to console email logging. |
| `GOOGLE_*`, `FACEBOOK_*`, `APPLE_*` (`CLIENT_ID` / `CLIENT_SECRET`) | Credentials for social providers enabled in `app.config.ts`. `APPLE_CLIENT_SECRET` is a JWT signed with the `.p8` private key (max 6-month expiry). |

### Test config

`.env.test` only overrides `DATABASE_URL`. `vitest.config.ts` pins `NODE_ENV=test`, which makes `src/config/index.ts` apply `src/config/test-overrides.ts` on top of `app.config.ts`:

- `registration.mode: 'open'` — allows `createTestSession()` to sign up the test admin via `POST /api/auth/sign-up/email`.
- `subscriptions.enabled: true`, with a test plan catalog: `starter` (no features), `pro` and `enterprise` (the modules' features plus `reports`, the suite's own feature — the infrastructure tests gate their throwaway routes and records with it, so they never depend on which modules gate what). Subscription-gated modules need it; the helper creates an active `pro` subscription for the test admin automatically.
- `uploads.dir: '/tmp/helix-test-uploads'`.

- `auth.socialProviders`: all off — an enabled provider needs OAuth credentials the suites' environments never have (the E2E server inherits this too).

The suite therefore never depends on what a product sets in `app.config.ts`.

**Other modes:** `createTestApp(overrides)` builds the app with `overrideConfig(config, overrides)` — e.g. `createTestApp({ registration: { mode: 'closed' } })` or `createTestApp({ subscriptions: { enabled: false } })`, the defaults a product ships with. Keep the default `app` for the session (`createTestSession()` signs up over HTTP, so it needs open registration): sessions live in the shared database and are signed with the same secret, so its cookies work on the second app too. Close every extra app in `afterAll`. References: `registration-routes.test.ts` and `bootstrap-routes.test.ts` (closed), `subscriptions-routes.test.ts` → _with subscriptions disabled_, `billing-webhook-routes.test.ts` (webhook not registered when disabled).

### OpenAPI spec export

`pnpm spec:export <file>` (`src/scripts/export-spec.ts`) writes the spec `@helix/api-client` is generated from — `pnpm export-spec` in `packages/api-client` calls it. It builds the app in memory with `src/config/spec-overrides.ts` applied (via `enableSpecExport()`, before `@/config` is imported), so the spec lists every route the codebase can expose regardless of `app.config.ts`. It needs no database (building the app opens no connection) and no `.env` (placeholder values only pass `src/env.ts`). The pre-commit hook runs it whenever a staged non-test file under `src/` changes, stages the result and regenerates the client (`lint-staged.config.js` — a function, so the export starts only after ESLint and Prettier have rewritten the sources), so the committed spec never lags behind the routes. `pre-push` (`.husky/pre-push`) re-exports it once more and blocks the push if it changed — this catches dependency bumps, rebases and `--no-verify` commits. The check is skipped while `apps/api` or the spec have uncommitted changes, since the export reads the working tree.

**While developing, the hooks are not enough:** `pnpm dev` never regenerates `@helix/api-client`, so after changing a route, a request/response schema (including `errorSchema` codes and `.meta({ id })`) or `src/config/permissions.ts`, run `pnpm spec:sync` from the repo root before the web uses it. See `packages/api-client/CLAUDE.md` → _Workflow when creating or modifying an API endpoint_.

`/api/docs` on a running server keeps serving the spec of its own config. **When a new setting registers routes conditionally** (like `subscriptions.enabled`), turn it on in `spec-overrides.ts`, or its routes vanish from the client. In this profile `requireSubscription()` skips its unknown-feature check, since the placeholder plan declares no features.

## Shared social provider utility (`src/lib/social-providers.ts`)

- `getConfiguredSocialProviders(config): string[]` — the social providers enabled in `config.auth.socialProviders` (credentials are guaranteed by config validation), whatever the mode.
- `getUsableSocialProviders(config): string[]` — the same list in open mode, `[]` in closed mode (email/password only). Backs both `GET /registration/status` (login/sign-up buttons) and `GET /me/providers` (account linking on `/me/security`), so the two never disagree. Both take only `{ registration, auth }`, so `social-providers.test.ts` passes plain objects — no mocking.

**When adding a new social provider:** update `auth.ts` (socialProviders config), `AppConfig` + `appConfigSchema` in `src/config/define-config.ts`, the credential map in `src/config/index.ts`, `env.ts` and `.env.example`.

## Module structure

```
src/modules/<feature>/
├── <feature>-schema.ts   ← Zod schemas + inferred types
├── <feature>-service.ts  ← database operations (factory function)
└── <feature>-routes.ts   ← Fastify route registrations
```

**Export only what another file imports.** The schema file exports the schemas and inferred types its routes and service use; the sort columns, the sorting and filter schemas, and any type nobody imports stay local. The service exports its factory, no `ReturnType` alias. `pnpm knip` (from the repo root) reports an export no file imports.

**Every route lives under `/api`** (`API_PREFIX`, `src/lib/api-prefix.ts`): `buildApp` registers all route plugins — public, better-auth, docs, static files and the `authenticated` scope — inside one plugin with `{ prefix: API_PREFIX }`. Route files declare paths without it (`app.get('/features', …)`), tests inject with it (`url: '/api/features'`), and the spec lists `/api` as its server with prefix-less paths (`@fastify/swagger`'s `stripBasePath`), so the generated client keeps `getFeatures`. `src/app.test.ts` checks that nothing answers outside the prefix. Code building a public URL from `env.BASE_URL` (the API's origin) adds `API_PREFIX` itself (`local-storage.ts`).

The entry point is `src/app.ts`, which exports `buildApp(database: Database, options?)` (`options.config` replaces the default settings and `options.billingWebhookAdapter` overrides `src/config/billing-webhook.ts` — both used by tests). Each route module is registered there, inside the `/api` scope, via `api.register(featureRoutes, { database })`, plus `config` when the module reads a setting.

## Hooks (`src/hooks/`)

The `src/hooks/` directory contains request-lifecycle hooks injected into the authenticated scope in `app.ts`.

| Hook | Factory | Purpose |
| --- | --- | --- |
| `require-auth.ts` | `createRequireAuth(auth)` | Validates the session cookie; attaches `request.sessionUser` |
| `require-permission.ts` | `createRequirePermission(database)` | Returns `requirePermission(resource, action) → PreHandler`; enforces RBAC per route. Only catalog pairs compile, and an undeclared one throws at registration |
| `require-subscription.ts` | `createRequireSubscription(database, config)` | Returns `requireSubscription(feature?) → PreHandler`; enforces active subscription (and plan feature) per route |
| `audit-request.ts` | `registerAuditRequest(app, recorder)` | Attaches `request.audit(action, resource, id?, metadata?)` globally — the audit recorder with the session user as actor |

### `requireSubscription` — subscription gate

Full reference (behavior matrix, admin bypass, past-due grace, trial): `src/modules/subscriptions/CLAUDE.md`. What a new module needs:

```ts
// app.ts — requireSubscription is created next to requirePermission in the authenticated scope
authenticated.register(featureRoutes, { database, requirePermission, requireSubscription })

// feature-routes.ts — subscription first, then permission
app.get('/feature', {
  preHandler: [requireSubscription('feature'), requirePermission('feature', 'view')],
  // ...
})
```

- The decision comes from the entitlements (`src/modules/subscriptions/entitlements.ts`), the same answer `GET /me/entitlements` gives the frontend. A denial is a 403 `{ message, code }` with `code` `subscription_required` or `feature_not_in_plan`; `requirePermission()` answers 403 `{ message: 'Forbidden', code: 'permission_denied' }`, so tests (and clients) can tell the two gates apart.
- `requireSubscription()` alone requires any active subscription; `requireSubscription('feature')` also requires the user's plan to list `'feature'` in `subscriptions.plans` (`src/app.config.ts`). A feature no plan declares throws at startup.
- With `subscriptions.enabled: false` it is a no-op, so adding it early is safe.
- Users whose role has `subscriptions:view` always pass.
- `todos` is the reference implementation.

## Pagination and sorting

Every list endpoint must be paginated and sortable. The reusable utilities live in `src/lib/`:

| File                    | Exports                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `src/lib/pagination.ts` | `paginationQuerySchema`, `PaginationQuery`, `getPaginationParams`, `buildPaginatedResponse`, `paginatedResponseSchema` |
| `src/lib/sorting.ts`    | `sortingQuerySchema`                                                                                                   |

**`paginationQuerySchema`** — Zod schema for `page` (int ≥ 1, default 1) and `pageSize` (int 1–100, default 10). Used as `querystring` in list routes.

**`sortingQuerySchema(columns)`** — factory that takes a non-empty tuple of sortable column names (module-specific) and returns a Zod schema for `sortBy` (optional enum) and `sortOrder` (default `"asc"`). The column list is declared in the module's schema file so TypeScript enforces valid values end-to-end.

**`buildPaginatedResponse(data, total, pagination)`** — assembles `{ data, total, page, pageSize, totalPages }` from the service result and the parsed query. Call this in every list route handler instead of constructing the object manually.

**`paginatedResponseSchema(itemSchema)`** — generic Zod factory for the paginated response shape. Used once per module to declare the `200` response schema.

### How they compose in a module

The three layers each consume one piece:

```
schema file  →  declares sort columns, merges pagination + sorting into one query schema
service      →  receives the combined query, applies getPaginationParams + orderBy
route        →  uses the combined querystring schema, calls buildPaginatedResponse
```

See the `todos` module (`todos-schema.ts`, `todos-service.ts`, `todos-routes.ts`) as the canonical reference. The `audit` module is a read-only example (no POST/PATCH/DELETE) that also demonstrates the full pagination + sorting pattern.

### Non-paginated "all" endpoints

Occasionally a module needs to expose **all** records in a single array — for example, to populate a select field in another module (e.g. `GET /roles/all` populates the role selector in the Users form). Add a `/all` endpoint only when another module genuinely needs it for a UI select component. This endpoint returns a plain array (no pagination shape) and has no `page`/`pageSize`/`sortBy` params.

**Never** replace the main `GET /xxx` list endpoint with a non-paginated variant. The list endpoint is always paginated; the `/all` variant is an optional addition for select-field use cases.

## Filtering

Every list endpoint can optionally support field-level filtering via the reusable utilities in `src/lib/filtering.ts`. Add filtering to a module when the list screen needs a filter panel.

| File                    | Exports                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| `src/lib/filtering.ts`  | `filterQuerySchema`, `buildFilterWhereClause`, `FilterWhereOptions`, `coerceCalendarDay`, `coerceInstant`, `searchQuerySchema`, `buildSearchClause`, `FilterLogic` |
| `src/lib/normalize-text.ts` | `normalizeText`, `normalizedValues`, `NormalizedFieldMap` — see _Normalized text columns_ |
| `src/lib/slug.ts` | `slugify`, `withUniqueSlug`, `SlugConfig`… — see _Slugs_ |

**`filterQuerySchema(allowedFields)`** — factory that accepts a non-empty tuple of filterable column names and returns a Zod schema with two fields:

- `filters` — accepts a JSON-encoded `FilterCondition[]` string; transforms to a typed array on validation; invalid JSON silently becomes `[]`
- `filterLogic` — `'AND' | 'OR'`, defaults to `'AND'`

A condition is `{ field, op, value? }`. Operators (`FILTER_OPERATORS`):

| `op` | SQL | `value` |
| --- | --- | --- |
| `eq`, `neq` | `=`, `<>` | string / number / boolean |
| `contains`, `startsWith`, `endsWith` | `LIKE '%v%'`, `'v%'`, `'%v'` on the field's normalized column, with `v` normalized (accent-, case- and whitespace-insensitive — see _Normalized text columns_); `ILIKE` on the column itself for a field without one. LIKE wildcards in `v` are escaped | string only — other types are ignored |
| `gt`, `gte`, `lt`, `lte` | `>`, `>=`, `<`, `<=` | number, or a date string with a `coerce` entry |
| `isNull`, `isNotNull` | `IS NULL`, `IS NOT NULL` | omitted |
| `in` | `IN (...)` | non-empty array of strings/numbers |
| `between` | `BETWEEN from AND to` (inclusive) | `[from, to]` — both set |

A condition whose value does not fit its operator is skipped, not rejected. A field outside the allowed list makes the whole `filters` param fall back to `[]` (same as invalid JSON).

Merge this into the module's `listQuerySchema` alongside pagination and sorting.

**Search box** — `searchQuerySchema` adds `search` (trimmed, blank → `undefined`, max 200 chars) and `buildSearchClause(term, normalizedColumns)` normalizes the term and turns it into a "contains" (`LIKE`, wildcards escaped) on any of the columns. **Pass normalized columns only** (`[features.normalizedTitle]`, see _Normalized text columns_): a plain column would be compared, case-sensitively, with an already-lowercased term. Combine both clauses with Drizzle's `and()`, which skips `undefined`: `and(buildFilterWhereClause(...), buildSearchClause(query.search, SEARCH_COLUMNS))`. Add `searchQuerySchema` to the export schema too, and audit only whether a search was used (`searched: Boolean(query.search)`), never the text.

**`buildFilterWhereClause(conditions, logic, columnMap, { coerce?, normalized? })`** — builds a Drizzle `SQL | undefined` from the parsed filter conditions. Returns `undefined` when the list is empty (no `.where()` added). Pass the result to both the data query and the count query so pagination totals remain consistent.

`normalized` maps a text field to its normalized column (`{ title: features.normalizedTitle }`), for the text operators — see _Normalized text columns_.

The optional `coerce` map transforms raw filter values before Drizzle receives them. This is required for columns whose DB type differs from the serialized URL value — the date columns. For array values (`in`, `between`) it runs on each item; a value it turns into `null` skips the condition:

```ts
import { coerceCalendarDay, coerceInstant } from '@/lib/filtering'

const FILTER_COERCE = {
  // `date` column (a calendar day): keeps `YYYY-MM-DD`, skips anything else
  date: coerceCalendarDay,
  // `timestamptz` column (an instant): an ISO datetime with its zone
  // (`…Z`, `…-03:00`) becomes a `Date`, anything else skips the condition
  createdAt: coerceInstant,
} as const
```

Without coercion, Drizzle will pass the raw string to PostgreSQL and the comparison will fail or error at runtime (an invalid date is a 500). **Never a hand-written `new Date(v)`**: an invalid string reaches Postgres as an invalid date (a 500). Both helpers are tested in `src/lib/filtering.test.ts`.

**A filter on an instant compares instants.** `coerceInstant` skips a bare day (`2025-03-20`): which instants a day spans depends on the user's time zone, which only the client knows — taken as UTC midnight, "on 3/20" would match almost nothing, "until 3/20" would drop the day itself and São Paulo would be three hours off. The client sends the instants that bound the user's days: the web's `FilterBar` `date` field holds days, and `toApiFilters()` (`apps/web/src/lib/list-filters.ts`) rewrites a condition on an instant field into them (`eq 3/20` → `between [3/20 00:00 local, 3/20 23:59:59.999 local]`, in ISO). Nothing changes here: the column goes in `FILTER_COLUMNS` and `FILTER_COERCE` like any other — `todos` filters `createdAt` this way.

### Adding filtering to a module

#### 1. Schema (`<feature>-schema.ts`)

```ts
import { filterQuerySchema } from '@/lib/filtering'

const FEATURE_FILTER_FIELDS = ['title', 'status', 'date'] as const

const featuresFilterQuerySchema = filterQuerySchema([...FEATURE_FILTER_FIELDS])

// Merge into the existing list query schema
export const featuresListQuerySchema = paginationQuerySchema
  .merge(featuresSortingSchema)
  .merge(featuresFilterQuerySchema)
```

Only list fields that users will actually filter by. The field names must match the Drizzle column map keys in the service (see below) and the `FilterFieldDef.name` values on the frontend.

#### 2. Service (`<feature>-service.ts`)

```ts
import { buildFilterWhereClause } from '@/lib/filtering'

const FILTER_COLUMNS = {
  title: features.title,
  status: features.status,
  date: features.date,
} as const

// Text fields: `contains`/`startsWith`/`endsWith` read the normalized copy
const NORMALIZED_FILTER_COLUMNS = {
  title: features.normalizedTitle,
} as const

// Only needed when a column type differs from the serialized URL value
const FILTER_COERCE = {
  date: coerceCalendarDay, // a `date` column — see `coerce` above
} as const

async function list(query: FeaturesListQuery) {
  const { limit, offset } = getPaginationParams(query.page, query.pageSize)
  const sortCol = SORT_COLUMNS[query.sortBy ?? 'createdAt']
  const sortFn = query.sortOrder === 'desc' ? desc : asc
  const where = buildFilterWhereClause(
    query.filters,
    query.filterLogic,
    FILTER_COLUMNS,
    { coerce: FILTER_COERCE, normalized: NORMALIZED_FILTER_COLUMNS }
  )

  const [data, [{ total }]] = await Promise.all([
    database.select().from(features).where(where).orderBy(sortFn(sortCol)).limit(limit).offset(offset),
    database.select({ total: count() }).from(features).where(where),
  ])
  return { data, total }
}
```

Always pass `where` to both queries — the count query drives pagination totals.

#### 3. Tests (`<feature>-routes.test.ts`)

Add a `describe('Filtering')` block inside `describe('GET /features')`:

| Test | What to verify |
|------|----------------|
| `filters` with `eq` on an enum field (e.g. `status=pending`) | returns only matching records |
| `filters` with `contains` on a text field | accent- and case-insensitive match (see _Normalized text columns_ → _Tests_) |
| `filters` with `gte` on a date/number field | range boundary respected |
| `filters` on an instant (`timestamptz`), with the instants a client sends for a day | both bounds of the day kept, a bare day or a value without a zone skipped (`describe('Filtering by an instant (createdAt)')`) |
| two conditions with `AND` logic | returns intersection |
| two conditions with `OR` logic | returns union |
| `filters=[]` (empty array) | returns all records |
| `filters=invalid-json` | returns all records (silent fallback) |

Seed the data via `testDb.insert` before each test case. Pass `filters` as a JSON-encoded string in the query string: `filters=JSON.stringify([{ field: 'status', op: 'eq', value: 'pending' }])`.

See `todos-routes.test.ts` (the reference module) for the reference implementation.

## Normalized text columns

Every text column users search or filter by "contains" — through the web's search box and `FilterPanel`, or another client (a site reading the API as a CMS) — gets a **normalized copy**: `title` → `normalizedTitle` (`normalized_title`). The service writes it on every insert and update with `normalizeText()` (`src/lib/normalize-text.ts`); the search and the text filters compare a normalized term with it. So `acao` finds `Ação`, `SAO  paulo` finds `São Paulo`, and `Árvore` sorts next to `arvore`.

It is written in TypeScript, not by the database (no generated column, no `unaccent` extension): the rule is explicit in the service layer, runs the same on any Postgres host, and the term and the stored value always go through the same function.

**The API contract does not change.** Clients keep filtering by `title`; the service maps it to the normalized column. The normalized columns are never in a response schema (the Zod serializer drops them) and never in `*_FILTER_FIELDS` or `*_SORT_COLUMNS`.

### The normalization (`normalizeText`)

In this order — the JSDoc of the function and the table in `normalize-text.test.ts` are the reference:

| Step | Example |
| --- | --- |
| `toLowerCase()` — locale-independent, before NFKD (so `İ` loses its dot in the next steps) | `RÁPIDO` → `rápido` |
| NFKD + remove the marks (`\p{M}`) — accents, also already-decomposed ones (macOS), ligatures and full-width forms | `ação` → `acao`, `ﬁ` → `fi`, `Ｆｕｌｌ` → `full` |
| `toLowerCase()` again — some characters only become capitals once decomposed | `ℌilbert` → `hilbert`, `㎒` → `mhz` |
| Map what does not decompose — `ß æ œ ø ł đ ð þ`, typographic quotes and dashes | `Straße` → `strasse`, `“a” — b` → `"a" - b` |
| Remove invisible format characters (`\p{Cf}`: soft hyphen, zero-width space, BOM) — text pasted from Word or the web | `co\u00ADope` → `coope` |
| Collapse whitespace (tabs, line breaks, NBSP) into one space and trim | `"  a \n b "` → `a b` |

Punctuation is kept (`e-mail` does not match `email`) and other scripts are only lowercased. Not normalized: rich text / HTML (`content`) — it would match tag names; searching it is a full-text concern (`tsvector`), a different pattern.

**Changing the rule** changes what every stored value should be: existing rows keep the old form until they are written again. Ship a rule change with a backfill that rewrites every normalized column.

### Adding a normalized column

**1. Table (`src/db/schema/<feature>.ts`)** — the column right after its source, `notNull()`, no default, and the map of source field → normalized column next to the table:

```ts
export const features = pgTable('features', {
  // ...
  title: text('title').notNull(),
  normalizedTitle: text('normalized_title').notNull(),
})

export const FEATURE_NORMALIZED_FIELDS = {
  title: 'normalizedTitle',
} as const satisfies Record<string, keyof typeof features.$inferInsert>
```

`notNull()` without a default makes every `insert(features)` that forgets the column a type error — the service, the seed and the tests alike. `pnpm db:generate` emits a plain `ADD COLUMN … NOT NULL`, which fails on a table with rows: on a dev database, `pnpm db:reset`, migrate, then `pnpm db:seed`. A table that already holds data the product must keep needs the column added nullable, a backfill, then `SET NOT NULL`.

**2. Writes (`<feature>-service.ts`)** — spread `normalizedValues(data, MAP)` into every insert and update. It returns a column for each mapped field present in `data` — every one on create, only the fields sent on a partial update — so the same line fits both:

```ts
await database.insert(features).values({ ...data, ...normalizedValues(data, FEATURE_NORMALIZED_FIELDS) })
await database.update(features).set({ ...data, ...normalizedValues(data, FEATURE_NORMALIZED_FIELDS) })
```

The seed does the same for its rows. Any other writer (a job, an import, raw SQL) must too — it is the price of doing it in TypeScript.

**3. Reads (`<feature>-service.ts`)**:

```ts
const SEARCH_COLUMNS = [features.normalizedTitle]                    // buildSearchClause
const NORMALIZED_FILTER_COLUMNS = { title: features.normalizedTitle } // buildFilterWhereClause → { normalized }
const SORT_COLUMNS = { title: features.normalizedTitle, /* … */ }      // sortBy=title
// .orderBy(sortFn(sortCol), asc(features.id)) — rows equal once normalized keep a stable order
```

| Operator | Column |
| --- | --- |
| `search`, `contains`, `startsWith`, `endsWith` | normalized (`LIKE`, both sides normalized) |
| `eq`, `neq`, `in` | original — exact, for a slug or a title a CMS looks up |
| `sortBy=title` | normalized, with `id` as the tie-breaker |

**4. Tests** — insert rows through a helper that fills the normalized columns the way the service does (`todoRow()` in `src/test/helpers.ts`), never by hand. In the route tests (`todos-routes.test.ts` → `describe('Normalized text columns')` is the reference), cover: search ignoring accents, case and repeated whitespace; `contains`/`startsWith`/`endsWith` on the normalized copy; `eq` still exact; `sortBy` on the field; the normalized columns absent from the response; `POST` fills them and `PATCH` refreshes only the fields sent.

**Index (optional):** a `contains` (`LIKE '%v%'`) cannot use a btree index, so without one it scans the table — fine up to tens of thousands of rows. For more, a trigram index on the normalized column (`index('features_normalized_title_trgm_idx').using('gin', t.normalizedTitle.op('gin_trgm_ops'))`) needs the `pg_trgm` extension, created in a custom migration (`drizzle-kit generate --custom --name pg_trgm`) — check the host supports it first.

## Slugs

A module whose records a public page shows by URL — a site reading the API as a CMS, at `/todos/comprar-pao` — gets a **`slug` column**. It is **internal to the API**: generated from a source field (`title`) on create, never accepted in a request body, never changed afterwards, and **always unique in its table** (a unique index). The admin (`apps/web`) never shows or edits it; it exists for the public URLs only. The API returns it in the entity (the site needs it to build its links) and looks a record up by it.

The helpers are in `src/lib/slug.ts`:

| Export | Does |
| --- | --- |
| `slugify(value, maxLength = 100)` | The slug of a text, pure — see the rules below. `''` when nothing is left |
| `SLUG_PATTERN` | `^[a-z0-9]+(?:-[a-z0-9]+)*$` |
| `SlugConfig` | `{ column, constraint, fallback, maxLength? }` — declared once per module, next to the table |
| `slugBase(source, config)` | `slugify(source)`, or `config.fallback` when that is empty. Throws when the fallback is not a valid slug |
| `freeSlug(base, taken, maxLength?)` | The first of `base`, `base-2`, `base-3`… not in `taken`, pure |
| `slugCandidatesPattern(base, maxLength?)` | The regex of every suffixed candidate `freeSlug()` can return: `^base-[0-9]+$` for a base of up to 92 characters (room for any suffix, so `todo` never matches `todo-list-2025`), `^<first 92>.*-[0-9]+$` for a longer one, whose candidates are cut |
| `uniqueSlug(database, config, source)` | A slug no row holds yet — one query (`slug = base OR slug ~ pattern`), then `freeSlug()` |
| `withUniqueSlug(database, config, source, write)` | Runs the insert with a `uniqueSlug()`, and again with a fresh one when a concurrent insert took it (unique violation on `config.constraint`, up to 5 attempts) |
| `distinctSlugs(sources, config)` | Slugs distinct among themselves, for rows written together into a table that holds none of them (the seed) |

### The rule (`slugify`)

In this order — the JSDoc of the function and the table in `slug.test.ts` are the reference:

| Step | Example |
| --- | --- |
| `normalizeText()` — the same rules as the normalized columns: lowercase, no accents, `ß` → `ss`, ligatures, typographic quotes and dashes → ASCII, invisible characters removed | `Ação RÁPIDA` → `acao rapida` |
| Remove apostrophes and quotes, so a word stays whole | `It's d’água` → `its dagua` |
| Every run of anything else (spaces, punctuation, other scripts, emoji) → one `-`, trimmed at the ends | `Versão 2.0 (2025)` → `versao-2-0-2025` |
| Cut at 100 characters: on the last hyphen before the limit when that keeps at least half, else hard | `a bbb…` (150 `b`s) → `a-bbb…` (100 chars), not `a` |

Only ASCII survives: a title in another script (`日本語`) gives `''`, and the config's `fallback` (`todo`) takes its place. A repeated base gets the first free numeric suffix (`acao`, `acao-2`, `acao-3`); a suffix that would pass the limit cuts the base, so the result never exceeds it.

**Stable on purpose.** Updating the title does not touch the slug: a public URL that changes breaks links and search rankings. A product that needs to change it (or keep old URLs working) adds a slug history table and a redirect — not part of the scaffold.

**Changing the rule** only affects new rows: existing slugs are URLs already out there, so they are never rewritten.

### Adding a slug to a module

**1. Table (`src/db/schema/<feature>.ts`)** — the column after its source, `notNull()`, a named unique index on `text_pattern_ops`, and the `SlugConfig` next to the table:

```ts
import type { SlugConfig } from '../../lib/slug' // relative: drizzle-kit loads this file

export const features = pgTable(
  'features',
  {
    // ...
    title: text('title').notNull(),
    slug: text('slug').notNull(),
  },
  (t) => [uniqueIndex('features_slug_unique').on(t.slug.op('text_pattern_ops'))]
)

export const FEATURE_SLUG = {
  column: features.slug,
  constraint: 'features_slug_unique',
  fallback: 'feature', // the entity name — must be a valid slug, slugBase() throws otherwise
} as const satisfies SlugConfig
```

**Why a `uniqueIndex` with `text_pattern_ops`, not `.unique()`:** `uniqueSlug()` looks up the base and its suffixed variants with an anchored regex (`slug ~ '^acao.*-[0-9]+$'`). Under a non-C collation (the databases here are `en_US.utf8`), the default operator class orders by the locale and serves only `=`, so that lookup reads the whole index on every create. With `text_pattern_ops` the planner turns the regex's fixed prefix into a range (`slug ~>=~ 'acao' AND slug ~<~ 'acap'`), and `=` (`getBySlug`) still uses it. It is still a unique index: a collision is a `23505` whose constraint is the index name, which `withUniqueSlug()` compares with `config.constraint`. The prefix only becomes a range when the planner sees the value — node-postgres plans each query with its parameters, but a `.prepare()`d (generic) plan loses it, so never prepare this query. The index does not serve `ORDER BY slug` or `<`/`>` by locale; nothing sorts by slug.

`pnpm db:generate` emits `ADD COLUMN … NOT NULL` + `CREATE UNIQUE INDEX`, which fails on a table with rows: on a dev database, `pnpm db:reset`, migrate, then `pnpm db:seed`. A table that already holds data the product must keep needs the column added nullable, a backfill with `distinctSlugs()`, then `SET NOT NULL` and the index.

**2. Contract (`<feature>-schema.ts`)** — `slug: z.string()` in the entity schema (with a `.describe()`), **never** in the create/update schemas: Zod strips an unknown key, so a `slug` sent in a body is silently ignored.

**3. Service (`<feature>-service.ts`)** — `create` wraps the insert in `withUniqueSlug()`; `update` does nothing (the slug is not in `UpdateFeatureInput`); add `getBySlug()`:

```ts
const [item] = await withUniqueSlug(database, FEATURE_SLUG, data.title, (slug) =>
  database.insert(features).values({ ...data, slug }).returning()
)

async function getBySlug(slug: string) {
  const [item] = await database.select().from(features).where(eq(features.slug, slug))
  return item ?? null
}
```

`write` is the insert alone. A failed statement aborts a surrounding transaction, so inside one, wrap the insert in a savepoint (`tx.transaction(...)`). Any other writer (the seed, an import, a job) fills the slug too — the column is `notNull()`, so forgetting it is a type error.

**4. Route (`<feature>-routes.ts`)** — `GET /features/by-slug/:slug`, same `preHandler` as `GET /features/:id`, 200 or 404. Give it an explicit `operationId: 'getFeatureBySlug'`: the name kubb derives from `by-slug/{slug}` repeats the word, and its mock then imports a types file that does not exist. Fastify prefers the static `by-slug` segment, so it never clashes with `/:id`.

**5. Seed and tests** — the seed computes the slugs with `distinctSlugs(titles, FEATURE_SLUG)`. The test row helper (`todoRow()` in `src/test/helpers.ts`) defaults `slug` to the title's slug plus a random suffix, so rows with the same title never collide; pass `slug` when the test looks it up. In the route tests (`todos-routes.test.ts` → `describe('Slug')` is the reference), cover: generated from the title; suffix on a repeated title; fallback for a title with no slug character; a 100-character title whose suffixed slugs are cut to stay at 100 (`'a'.repeat(100)` → `aaa…-2`, which runs the long-base lookup); concurrent creates with the same title get distinct slugs; a `slug` in the `POST`/`PATCH` body ignored; a title change keeps the slug; the unique index; `GET /by-slug/:slug` 200 and 404; and the route in _Permission enforcement_. The helpers themselves (the rule, the candidate pattern, the retry with a fake `write`: a collision then success, another constraint rethrown at once, giving up after 5) are tested once in `src/lib/slug.test.ts`.

**Public access:** `GET /by-slug/:slug` sits behind the session, the permission and the subscription like every other route, so a site calls it with a service account. An unauthenticated public read (API keys, a public scope) is a separate pattern.

Only images, PDF, plain text, audio and video open in the browser; every other file downloads in a sandbox — see `src/modules/uploads/CLAUDE.md` → _Serving files_.

### Adding file attachments to a module

Use `todos` as the reference implementation; the step-by-step guide (multi-file junction table and single-file FK column) is in `src/modules/uploads/CLAUDE.md` → _Adding uploads to another module_. Summary:

1. Multi-file: junction table `xxx_attachments(xxx_id FK cascade, upload_id FK cascade)`. Single file: nullable `xxx.file_id` FK → `uploads.id` `on delete set null`
2. Response embeds `attachments: uploadSchema.array()` / `file: uploadSchema.nullable()`; create/update accept `attachmentIds` / `fileId`
3. Service: `assertUsableUploads()` on create/update (a record references only uploads its author uploaded — 400 `invalid_upload` — and a typed field only files of its type, `{ id, accept: IMAGE_TYPES }` — 400 `invalid_upload_type`); load uploads on reads; sync junction rows on create/update; on delete, collect upload IDs → delete the record → delete the `uploads` rows → delete storage keys (best-effort)
4. Accept `storage: StorageProvider` in route options and pass it to the service factory
5. **Register every new column in `src/config/upload-references.ts`**, with the guard of the record's `GET` route — otherwise the orphan cleanup job deletes those uploads after the grace period, and nobody but the uploader and `uploads:view` can open their files. Each column gets its cases in `upload-files-routes.test.ts` → _Who may read a file_
6. Images inside a rich text field (`onUploadImage`): a junction table `xxx_<field>_images` the service fills from the HTML with `uploadIdsInHtml()` (`src/lib/rich-text-uploads.ts`), checked and registered like the others — see `src/modules/uploads/CLAUDE.md` → _Images inside rich text_

## PDF export

Modules can expose a `GET /xxx/export` endpoint that streams a PDF report to the client. The rendering happens server-side via `@react-pdf/renderer`. See `src/lib/pdf/CLAUDE.md` for the rendering infrastructure (templates, `BaseDocument`, colors, styles).

Use `todos` as the reference implementation (`todos-schema.ts`, `todos-service.ts`, `todos-routes.ts`, `templates/todos-report.tsx`).

### When to add PDF export

Add a PDF export endpoint when the module has a list screen with filters and the user needs to take that data offline. It always mirrors the list endpoint's sort/filter params — minus pagination.

### Adding PDF export to a module

#### 1. Schema (`<feature>-schema.ts`)

The export query reuses the existing sorting and filter schemas, with no pagination:

```ts
export const featuresExportQuerySchema = featuresSortingSchema.merge(featuresFilterQuerySchema)
export type FeaturesExportQuery = z.infer<typeof featuresExportQuerySchema>
```

#### 2. Template (`src/modules/<feature>/templates/<feature>-report.tsx`)

See `src/lib/pdf/CLAUDE.md` for the full template guide. The exported function signature must be:

```ts
export async function renderFeatureReport(items: FeatureRow[]): Promise<Buffer>
```

#### 3. Service (`<feature>-service.ts`)

Add `generateReport` to the factory. Always cap with `.limit(5000)` — an unbounded export is a DoS vector. Load the template via dynamic `import()` so the PDF runtime is only initialised when the route is actually called:

```ts
async function generateReport(query: FeaturesExportQuery): Promise<Buffer> {
  const sortCol = SORT_COLUMNS[query.sortBy ?? 'createdAt']
  const sortFn = query.sortOrder === 'desc' ? desc : asc
  const where = buildFilterWhereClause(
    query.filters,
    query.filterLogic,
    FILTER_COLUMNS,
    { coerce: FILTER_COERCE, normalized: NORMALIZED_FILTER_COLUMNS },
  )

  const data = await database
    .select()
    .from(features)
    .where(where)
    .orderBy(sortFn(sortCol))
    .limit(5000)

  const { renderFeatureReport } = await import('./templates/feature-report')
  return renderFeatureReport(data)
}

return { list, getById, create, update, remove, generateReport }
```

#### 4. Route (`<feature>-routes.ts`)

The export endpoint uses the same `view` permission as the list. Wrap `generateReport` in a try/catch — render failures must return a clean 500, not leak a stack trace. Audit after success with a minimal metadata object (never the raw query params — `filters` can contain arbitrary user data):

```ts
app.get(
  '/features/export',
  {
    schema: {
      tags: ['features'],
      description: 'Export features as PDF',
      querystring: featuresExportQuerySchema,
    },
    preHandler: requirePermission('features', 'view'),
  },
  async (request, reply) => {
    let buffer: Buffer
    try {
      buffer = await service.generateReport(request.query)
    } catch {
      return reply.status(500).send({ message: 'Failed to generate report' })
    }
    const date = new Date().toISOString().split('T')[0]
    await request.audit('export', 'features', undefined, {
      sortBy: request.query.sortBy,
      sortOrder: request.query.sortOrder,
      filterLogic: request.query.filterLogic,
      filterCount: request.query.filters?.length ?? 0,
    })
    return reply
      .header('Content-Type', 'application/pdf')
      .header('Content-Disposition', `attachment; filename="features-${date}.pdf"`)
      .send(buffer)
  },
)
```

> **Note**: `'export'` must be present in the `action` union in `src/modules/audit/audit-service.ts` and `src/types.ts`. It is already registered — no change needed for new modules.

> **Note**: Binary responses cannot carry a Zod `response` schema with `fastify-type-provider-zod`. Omitting `response` from the schema is intentional and correct for this endpoint type.

## Errors the client can act on (`DomainError`)

Throw a `DomainError` (`src/lib/domain-errors.ts`) — from the service or the handler — instead of building the response by hand. `registerDomainErrorHandler()` (installed by `buildApp` before any route) answers it with its status and `{ message, code }`; everything else goes on to Fastify's default handler (validation 400s, 500s).

```ts
import { DomainError, errorSchema } from '@/lib/domain-errors'

// service or handler
throw new DomainError(409, 'name_taken', 'A role with this name already exists')

// route schema — declare every status a DomainError can answer
response: { 201: roleSchema, 409: errorSchema('name_taken') },
```

- `code` is stable snake_case — the frontend translates it from `errors.<code>` in the module's locale (`apps/web/src/lib/api-errors.ts`). `message` is English, for logs and API users. Add the translation in both web locales when you add a code.
- `errorSchema(...codes)` documents the codes in the OpenAPI spec. Its `code` stays a plain string, because the same status may also carry Fastify's codes (a validation 400 is `FST_ERR_VALIDATION`). A missing status in `response` makes serialization fail.
- **Database constraints:** never let a violation surface as a 500 when the client can act on it. Read the Postgres code with `src/lib/pg-errors.ts` (Drizzle wraps driver errors, so the code may be on the error or on its `cause`; never read `error.code` directly) and turn it into a `DomainError`; when one status has several causes (two unique indexes), tell them apart with `getPgErrorConstraint(error)`.
- Current codes:

| Module | Status | Codes |
| --- | --- | --- |
| roles | 403, 409 | `admin_role_locked`, `role_not_editable` (service `update()`/`remove()` — admin role and privilege ceiling), `name_taken` (service, unique `name`), `default_role`, `role_in_use` (service `remove()`) |
| users / accounts | 403, 404, 409 | `admin_role_not_assignable`, `admin_user_locked`, `role_not_assignable`, `user_not_editable` (users service — admin role and privilege ceiling), `role_not_found`, `user_not_found`, `email_taken` (`RoleNotFoundError`, `EmailTakenError` in account provisioning; PATCH maps `user_email_unique`) |
| subscriptions | 400, 409 | `user_not_found` (FK), `live_subscription_exists`, `external_id_taken` (`toDomainError()` in `subscriptions-routes.ts`) |
| permissions | 400, 403, 404 | `unknown_permissions`, `missing_required_permissions`, `admin_role_locked`, `role_not_editable`, `permissions_not_grantable` (admin role and privilege ceiling), `role_not_found` |
| todos | 400 | `invalid_upload`, `invalid_upload_type` (`assertUsableUploads()`, `src/lib/upload-ownership.ts`) |
| me | 400, 429 | `current_password_required`, `invalid_password`, `email_change_rejected`, `password_change_rejected`, `too_many_attempts` (`me-service` — re-authentication and `createAttemptLimiter()`, `src/lib/attempt-limiter.ts`) |
| requireSubscription / requirePermission | 403 | `subscription_required`, `feature_not_in_plan`, `permission_denied` (sent by the hooks) |

Plain "not found" 404s of `GET /xxx/:id` stay `reply.status(404).send({ message })` — nothing for the client to do but show "not found". Tested in `src/lib/domain-errors.test.ts` (status + body, inside plugins; validation 400 and 500 untouched).

## Creating a new module (CRUD)

Use the `todos` module as the reference implementation. Follow this order exactly.

### 0. Register the resource (`src/config/permissions.ts`)

Every module that exposes user-facing data must declare its resource and actions here. This is the single source of truth for what permissions exist — bootstrap, test helpers, and the `GET /permissions/resources` endpoint all read from it.

```ts
// src/config/permissions.ts
{
  resource: "features",
  label: "Features",
  actions: ["view", "create", "edit", "delete"],
},
```

Declaring the resource is enough for the rest of the system: bootstrap grants it to the Admin role, the frontend permission editor lists it, and `PUT /roles/:id/permissions` accepts it (anything undeclared is rejected with 400).

`PermissionAction = "view" | "create" | "edit" | "delete"` is the full set of supported actions. TypeScript enforces this via `satisfies` — adding an unsupported action is a compile error. If the module genuinely needs a new action type, extend `PermissionAction` first.

The catalog is `as const`, so the names are typed from it:

- `requirePermission(resource, action)` accepts only pairs the catalog declares — `requirePermission('feature', 'view')` (typo) and `requirePermission('audit', 'edit')` (undeclared action) do not compile. A pair that slips past the types (a cast) throws when the route registers, so the API does not start — never a route that answers 403 to everyone.
- `request.audit()`'s `resource`, the seed's permission lists (`satisfies Permission[]`) and `ALL_PERMISSIONS` use the same types.
- The resource names go into the spec as the `PermissionResource` enum (`GET /permissions/resources`), so the frontend's `PageAccess`, `hasPermission()` and `<HasPermission>` reject a typo too — after `pnpm spec:sync`.

**Requirements** — then declare in `PERMISSION_REQUIREMENTS` (same file) what each action needs to be usable: a permission another one guards without which the page does not load or cannot finish its main task. A page that loads the record needs `view`; a required field fed by another module's route needs that route's permission — a select (`roles:view` for `RoleSelectField`), a required upload (`uploads:create`):

```ts
'features:create': ['features:view', 'uploads:create'], // lands on the list; a required file field
'features:edit': ['features:view', 'roles:view'],       // loads the record; RoleSelectField reads GET /roles/all
'features:delete': ['features:view'],                   // deleted from the list
```

An optional action inside a page is not a requirement: the todos edit form opens with the files the todo has, so `todos:edit` does not need `uploads:create` — a role may edit todos without uploading files (replacing one then answers 403). Requiring it would hand every editor a permission the admin may want to keep apart.

Keys and values are typed `'resource:action'` pairs, so a typo does not compile. Direct requirements only — chains resolve on their own. `GET /permissions/resources` serves them (`requires`): the permission editor checks the requirements of what the admin checks, and unchecks what depends on what they uncheck. `PUT /roles/:id/permissions` refuses grants without them (400 `missing_required_permissions`). Without a requirement, a role holding only `features:edit` reaches an edit page whose loader gets a 403.

### 1. Schema (`<feature>-schema.ts`)

Declare all Zod schemas for the module. The main schema (`featureSchema`) describes the object returned by the API. The others describe request bodies and the paginated list:

```ts
import z from 'zod'
import {
  paginatedResponseSchema,
  paginationQuerySchema,
} from '@/lib/pagination'
import { sortingQuerySchema } from '@/lib/sorting'

export const featureSchema = z
  .object({
    id: z.string(),
    title: z.string(),
    // ...other fields
    createdAt: z.date(),
    updatedAt: z.date(),
  })
  .meta({ id: 'Feature', title: 'Feature' })

export const createFeatureSchema = z.object({
  title: z.string().min(1).max(200),
  // ...mutable fields — always add .max() to mirror the frontend constraint
})

export const updateFeatureSchema = z.object({
  title: z.string().min(1).max(200).optional(),
  // ...optional fields
})

export type CreateFeatureInput = z.infer<typeof createFeatureSchema>
export type UpdateFeatureInput = z.infer<typeof updateFeatureSchema>

// Pagination + sorting for the list endpoint
const FEATURE_SORT_COLUMNS = ['title', 'createdAt'] as const

const featuresSortingSchema = sortingQuerySchema([...FEATURE_SORT_COLUMNS])
export const featuresListQuerySchema = paginationQuerySchema.merge(
  featuresSortingSchema
)
export type FeaturesListQuery = z.infer<typeof featuresListQuerySchema>

export const paginatedFeaturesSchema = paginatedResponseSchema(
  featureSchema
).meta({
  id: 'PaginatedFeatures',
  title: 'PaginatedFeatures',
})
```

Choose `FEATURE_SORT_COLUMNS` based on the fields users are likely to sort by. Always include `createdAt` as a fallback — it is the default sort column when `sortBy` is absent.

**Always add `.meta({ id, title })` to the main entity schema.** This registers it in Zod's global registry so `@fastify/swagger` emits it as a named `$ref` component (`components/schemas/Feature`) instead of inlining the object schema in every response. Without it, kubb generates duplicate inline types per endpoint and hits a naming collision when the schema contains an enum field, producing a broken array type (e.g. `Feature[] → StatusEnum[]`).

### 2. Database schema (`src/db/schema/<feature>.ts`)

Declare the table with Drizzle. Add the export to `src/db/schema/index.ts`:

```ts
import { pgTable, text, timestamp } from 'drizzle-orm/pg-core'
import { uuidv7 } from 'uuidv7'

export const features = pgTable('features', {
  id: text('id')
    .primaryKey()
    .$defaultFn(() => uuidv7()),
  title: text('title').notNull(),
  createdAt: timestamp('created_at', { withTimezone: true })
    .notNull()
    .defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true })
    .notNull()
    .defaultNow()
    .$onUpdateFn(() => new Date()),
})
```

**Dates and times.** Pick the column by what the value is:

| The value is… | Column | Contract (Zod) | Example |
| --- | --- | --- | --- |
| an instant (when something happened or ends) | `timestamp(name, { withTimezone: true })` — `timestamptz` | `z.date()` in the entity (serialized as ISO, UTC) | `createdAt`, `expiresAt`, `publishedAt` |
| a calendar day, no time | `date(name, { mode: 'string' })` | `z.iso.date()` — `YYYY-MM-DD`, in and out | `todos.date`, a birthday, a due date |

**Never `timestamp` without a time zone.** It stores a wall time with no zone: `defaultNow()` and `now()` write it in the Postgres session's time zone while Drizzle reads it back as UTC, so a database outside UTC shifts every date. `src/db/schema/schema.test.ts` fails on any `timestamp` column without `withTimezone` (and checks `defaultNow()` on a session in `America/Sao_Paulo`). A calendar day stored as an instant (UTC midnight) is the opposite trap: west of UTC the browser shows the day before — it is a `date`. The web parses a `YYYY-MM-DD` with `parseISO()`, which reads it as local midnight (the right day), and sends what `DateInput` gives (`YYYY-MM-DD`). Filter a `date` column with `coerceCalendarDay`, an instant with `coerceInstant` (_Filtering_).

Every text column users will search or filter by "contains" gets a normalized copy (`normalizedTitle`) — see _Normalized text columns_. A record a public page shows by URL gets a `slug` — see _Slugs_.

**Every foreign key gets an index.** Postgres creates one for a primary key or a unique constraint, never for the referencing side of a foreign key, so without it an `ON DELETE` on the referenced row and every lookup by the column (a filter, a join, the upload references of `GET /files/*`) scan the whole table. Name it `<table>_<column>_idx`:

```ts
(t) => [index('features_category_id_idx').on(t.categoryId)]
```

A column that already leads a composite primary key or unique index is covered — `todo_attachments` (`PRIMARY KEY (todo_id, upload_id)`) indexes `upload_id` alone and not `todo_id`. Indexes for performance only (sorting, filtering, the trigram of _Normalized text columns_) are added when the table is expected to grow, not by default.

After creating the schema, generate and apply the migration:

```bash
pnpm db:generate --name features   # the table's name — see _Scripts_ for the naming rule
pnpm db:migrate
pnpm db:migrate:test
```

### 3. Service (`<feature>-service.ts`)

A factory function that receives `database: Database` and returns the data access methods. No business logic beyond SQL — any logic that is not plain SQL must be extracted and tested separately.

`list()` always accepts `FeaturesListQuery` and applies both pagination and ordering. The `SORT_COLUMNS` map translates the string column name (from the query param) to the actual Drizzle column reference. The default sort column is used when `sortBy` is absent.

The example below has no normalized columns. With them (see _Normalized text columns_), `create` and `update` spread `normalizedValues(data, FEATURE_NORMALIZED_FIELDS)` into `.values()` / `.set()`, and `SEARCH_COLUMNS`, the text filters and `SORT_COLUMNS.title` read the normalized copy. Forgetting it in `create` is a type error; in `update` it is not, and the search goes stale silently.

```ts
import { asc, count, desc, eq } from 'drizzle-orm'
import type { Database } from '@/db'
import { features } from '@/db/schema'
import { getPaginationParams } from '@/lib/pagination'
import type {
  CreateFeatureInput,
  FeaturesListQuery,
  UpdateFeatureInput,
} from './feature-schema'

const SORT_COLUMNS = {
  title: features.title,
  createdAt: features.createdAt,
} as const

export function createFeatureService(database: Database) {
  async function list(query: FeaturesListQuery) {
    const { limit, offset } = getPaginationParams(query.page, query.pageSize)
    const sortCol = SORT_COLUMNS[query.sortBy ?? 'createdAt']
    const sortFn = query.sortOrder === 'desc' ? desc : asc
    const [data, [{ total }]] = await Promise.all([
      database
        .select()
        .from(features)
        .orderBy(sortFn(sortCol))
        .limit(limit)
        .offset(offset),
      database.select({ total: count() }).from(features),
    ])
    return { data, total }
  }

  async function getById(id: string) {
    const [item] = await database
      .select()
      .from(features)
      .where(eq(features.id, id))
    return item ?? null
  }

  async function create(data: CreateFeatureInput) {
    const [item] = await database.insert(features).values(data).returning()
    return item
  }

  async function update(id: string, data: UpdateFeatureInput) {
    const [item] = await database
      .update(features)
      .set(data)
      .where(eq(features.id, id))
      .returning()
    return item ?? null
  }

  // `false` when the id did not exist — the route then skips the audit entry
  async function remove(id: string): Promise<boolean> {
    const deleted = await database
      .delete(features)
      .where(eq(features.id, id))
      .returning({ id: features.id })
    return deleted.length > 0
  }

  return { list, getById, create, update, remove }
}
```

### 4. Routes (`<feature>-routes.ts`)

A Fastify plugin that receives `{ database, requirePermission }` as options (plus `requireSubscription`, `storage`, `emailProvider` or `auth` only when the module needs them). Every route must have a `schema` with `tags`, `description`, and the Zod schemas for body/params/response, **plus** a `preHandler` that enforces the matching permission:

| Route                  | Permission        |
| ---------------------- | ----------------- |
| `GET /features`        | `features:view`   |
| `GET /features/:id`    | `features:view`   |
| `POST /features`       | `features:create` |
| `PATCH /features/:id`  | `features:edit`   |
| `DELETE /features/:id` | `features:delete` |

Every mutation handler (POST, PATCH, DELETE) must call `request.audit()` after the service call succeeds. `request.audit` is injected by `registerAuditRequest` (registered once in the authenticated scope in `app.ts`) — route modules do **not** need to receive or import `auditService`. Do not call `request.audit()` on read-only routes (`GET`).

The method signature is:

```ts
request.audit(action, resource, resourceId?, metadata?)
```

- `action` — `"create"`, `"edit"`, or `"delete"`
- `resource` — a resource of `src/config/permissions.ts` (`PermissionResource`), or `me`
- `resourceId` — the id of the affected record (omit or pass `undefined` if not applicable)
- `metadata` — pass `request.body` for create/edit; omit for delete (no body)

Failures are caught and logged server-side automatically (by the audit recorder, `src/modules/audit/audit-recorder.ts`) — never call `.catch()` yourself. `action` is `AuditAction` and `resource` is `AuditResource` (a resource of `src/config/permissions.ts`, or `me`), so a typo does not compile. Assert the entry in the route tests — `findAuditLogs(action, resource, id)` — for create and edit as well as delete.

```ts
import z from 'zod'
import type { FastifyTypedInstance, RequirePermission } from '../../types'
import type { Database } from '../../db'
import {
  featureSchema,
  createFeatureSchema,
  updateFeatureSchema,
  featuresListQuerySchema,
  paginatedFeaturesSchema,
} from './feature-schema'
import { createFeatureService } from './feature-service'
import { buildPaginatedResponse } from '@/lib/pagination'

export async function featureRoutes(
  app: FastifyTypedInstance,
  {
    database,
    requirePermission,
  }: { database: Database; requirePermission: RequirePermission }
) {
  const service = createFeatureService(database)

  app.get(
    '/features',
    {
      schema: {
        tags: ['features'],
        description: 'List features',
        querystring: featuresListQuerySchema,
        response: { 200: paginatedFeaturesSchema },
      },
      preHandler: requirePermission('features', 'view'),
    },
    async (request) => {
      const { data, total } = await service.list(request.query)
      return buildPaginatedResponse(data, total, request.query)
    }
  )

  app.get(
    '/features/:id',
    {
      schema: {
        tags: ['features'],
        description: 'Get a feature by id',
        params: z.object({ id: z.string() }),
        response: {
          200: featureSchema,
          404: z.object({ message: z.string() }),
        },
      },
      preHandler: requirePermission('features', 'view'),
    },
    async (request, reply) => {
      const item = await service.getById(request.params.id)
      if (!item) return reply.status(404).send({ message: 'Feature not found' })
      return item
    }
  )

  app.post(
    '/features',
    {
      schema: {
        tags: ['features'],
        description: 'Create a feature',
        body: createFeatureSchema,
        response: { 201: featureSchema },
      },
      preHandler: requirePermission('features', 'create'),
    },
    async (request, reply) => {
      const item = await service.create(request.body)
      await request.audit('create', 'features', item.id, request.body)
      return reply.status(201).send(item)
    }
  )

  app.patch(
    '/features/:id',
    {
      schema: {
        tags: ['features'],
        description: 'Update a feature',
        params: z.object({ id: z.string() }),
        body: updateFeatureSchema,
        response: {
          200: featureSchema,
          404: z.object({ message: z.string() }),
        },
      },
      preHandler: requirePermission('features', 'edit'),
    },
    async (request, reply) => {
      const item = await service.update(request.params.id, request.body)
      if (!item) return reply.status(404).send({ message: 'Feature not found' })
      await request.audit('edit', 'features', request.params.id, request.body)
      return item
    }
  )

  app.delete(
    '/features/:id',
    {
      schema: {
        tags: ['features'],
        description: 'Delete a feature',
        params: z.object({ id: z.string() }),
        response: { 204: z.null().describe('Feature deleted') },
      },
      preHandler: requirePermission('features', 'delete'),
    },
    async (request, reply) => {
      // 204 either way (idempotent), but only a real deletion is audited
      if (await service.remove(request.params.id)) {
        await request.audit('delete', 'features', request.params.id)
      }
      return reply.status(204).send(null)
    }
  )
}
```

**Key rule**: the `request.audit()` call must come **after** the service call succeeds. For handlers with an early 404 return, place it after the guard so it only fires on the success path.

### 5. Register in `app.ts`

All modules that require authentication must be registered inside the `authenticated` scope. `requirePermission` is passed to every module; `request.audit` is available automatically via `registerAuditRequest` — route modules do not need to receive `auditService`.

```ts
import { featureRoutes } from './modules/feature/feature-routes'

// buildApp() — the authenticated scope (inside the `/api` scope) already exists; only add the register call:
api.register(async (authenticated) => {
  authenticated.addHook('preHandler', createRequireAuth(auth))
  registerAuditRequest(authenticated, audit)

  const requirePermission = createRequirePermission(database)
  const requireSubscription = createRequireSubscription(database, config)

  // ...existing modules
  authenticated.register(featureRoutes, { database, requirePermission }) // ← add here
})
```

A module that reads a setting receives `config` in its options (`{ database, config, requirePermission }`) — never `import { config } from '@/config'` inside a module, or tests cannot run it in another mode. Routes that must exist only under a config flag are registered conditionally (`if (config.subscriptions.enabled) …`) — and the flag must then be turned on in `src/config/spec-overrides.ts`, or the routes disappear from the generated client (see _OpenAPI spec export_).

Registering outside `authenticated` (directly in the `api` scope) will leave the routes publicly accessible; registering on `app` itself would also put them outside `/api`.

## Testing

**Commands:**

```bash
pnpm test          # single run
pnpm test:watch    # watch mode
```

### Philosophy

Backend tests are route integration tests: they exercise the full Fastify stack (validation, serialization, routing) against a real test database. This ensures the entire stack works — Zod schema, Drizzle, database constraints — without any abstraction in the middle.

### What NOT to do

- **Do not mock the database.** Replacing the database with a mock eliminates exactly what makes these tests valuable: verifying that the SQL is correct, that constraints are respected, and that Drizzle behaves as expected.
- **Do not test the service directly when it has no logic of its own.** The `audit` service, for example, is pure SQL delegated to Drizzle — testing `createAuditService` in isolation would only re-assert that `.insert().returning()` works, which is not this project's responsibility. Route tests already cover it.
- **Do not write E2E tests here.** Playwright E2E tests live in `apps/web/e2e/` and cover journeys across the web and this API (`pnpm e2e:server`). Do not duplicate that level here.

### Test infrastructure

Test files run **serially** (`fileParallelism: false` in `vitest.config.ts`) against one shared database (`helix_test`, port 5436, from `.env.test`) — never assume a clean DB, clean what your file touches. `NODE_ENV=test` applies `src/config/test-overrides.ts` (see _Test config_).

The helpers in `src/test/helpers.ts` provide:

- `testDb` — Drizzle instance on the test database
- `createTestApp(overrides?)` — `buildApp(testDb)` with the test config, or with `overrides` merged on top (another mode — see _Test config_ → _Other modes_). For a custom billing adapter, call `buildApp(testDb, { billingWebhookAdapter })` directly
- `createTestSession(app)` — signs up `test@test.com` with the `__test_admin__` role (every permission in `ALL_PERMISSIONS`) and an active `pro` subscription; returns the cookie string. That role only holds every permission — it is **not** the admin role (`isAdmin`), so it is the "moderator granted everything" the admin role must stay out of reach of
- `getTestUser()` — the user created by `createTestSession()` (look it up by email, never by row order)
- `createRoleWithPermissions(grants)` — a fresh role with exactly the given permissions, for permission enforcement tests
- `createAdminRole()` — the admin role (`isAdmin`), as the bootstrap creates it; at most one exists, and `cleanupRoles()` removes it
- `createSessionWithRole(app, roleId)` — signs up a fresh user with that role and returns its cookie (pair it with the two above)
- `findAuditLogs(action, resource, resourceId)` — the audit entries written for one record
- `grantActiveSubscription(email, planId = 'pro')` — an active subscription for that user. Restricted users on a **subscription-gated** route need it (see _Permission enforcement tests_)
- `todoRow(values)` — a `todos` row for `testDb.insert(todos)` with its normalized columns filled and a unique `slug` (title + random suffix, unless given). A module with normalized columns or a slug adds its own (`featureRow()`)
- Cleanup: `cleanupAuth()` (session, account, verification, user **and all roles**), `cleanupUsers()` / `cleanupRoles()` (everything except the test user / test role), `cleanupAuditLogs()`, `cleanupSubscriptions()`, `cleanupTodos()`, `cleanupUploads()`

**Infrastructure tests never borrow a module.** A helper that works on any module's tables or routes (slugs, upload references, the orphan cleanup, `requireSubscription`) is tested on structures of the test's own, so it stays tested in a product that has none of the scaffold's modules: a `pgTable` created in `beforeAll` and dropped in `afterAll` (in no migration — `src/lib/slug.test.ts`; `src/test/scratch-tables.ts` for a record with a single-file column and an attachments table, with `testDocumentReferences()` to register them), a bare Fastify route with the real hooks (`subscriptions-routes.test.ts` → `createGatedApp()`), a resource every product keeps (`users`, `roles`, `audit`) and the `reports` feature of `test-overrides.ts`. A module's own rules are tested in its own test file.

When adding a new module, add a `cleanupFeature()` function to `helpers.ts`:

```ts
import { features } from '@/db/schema/feature'

export async function cleanupFeature() {
  await testDb.delete(features)
}
```

### Test file structure (`<feature>-routes.test.ts`)

1. Create a session in `beforeAll` and clean up auth in `afterAll`

3. Include one top-level 401 test (outside any `describe`) to verify the module is inside the authenticated scope

| Endpoint               | Required cases                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /features`        | empty list returns `{ data: [], total: 0, page: 1, pageSize: 10, totalPages: 0 }`; list with items; `page`/`pageSize` applied correctly (correct slice returned); `sortBy`/`sortOrder` applied (items in expected order) |
| `GET /features/:id`    | 404 for unknown id; returns correct item                                                                                                                                                                                 |
| `POST /features`       | 201 with correct body; 400 for invalid body                                                                                                                                                                              |
| `PATCH /features/:id`  | 404 for unknown id; updates and returns correct fields (fields not sent remain unchanged)                                                                                                                                |
| `DELETE /features/:id` | 204 for existing item (one audit entry — `findAuditLogs`); 204 for unknown id and no audit entry (use a fresh id, e.g. `missing-${crypto.randomUUID()}`)                                                                                                                                                                                |

A module with normalized columns also covers what _Normalized text columns_ → _Tests_ lists (search without accents, `eq` still exact, `PATCH` refreshing the copy, columns absent from the response). A module with a slug covers what _Slugs_ → _Adding a slug to a module_ → step 5 lists.

### Permission enforcement tests

Every route module must include a `describe("Permission enforcement")` block that verifies each route returns 403 when the session user's role lacks the required permission. Use `createRoleWithPermissions` to build a restricted session:

```ts
import { eq } from 'drizzle-orm'
import {
  createRoleWithPermissions,
  cleanupUsers,
  cleanupRoles,
} from '@/test/helpers'
import { user } from '@/db/schema/authentication'

describe('Permission enforcement', () => {
  async function createRestrictedSession(
    grants: { resource: string; action: string }[]
  ) {
    const role = await createRoleWithPermissions(grants)
    const email = `restricted-features-${Date.now()}@test.com`
    const res = await app.inject({
      method: 'POST',
      url: '/api/auth/sign-up/email',
      payload: JSON.stringify({
        email,
        name: 'Restricted',
        password: 'Password123!',
      }),
      headers: { 'content-type': 'application/json' },
    })
    await testDb
      .update(user)
      .set({ roleId: role.id })
      .where(eq(user.email, email))
    const setCookie = res.headers['set-cookie']
    const cookies = Array.isArray(setCookie) ? setCookie : [setCookie ?? '']
    return cookies.map((c) => c.split(';')[0]).join('; ')
  }

  beforeEach(async () => {
    await cleanupUsers()
    await cleanupRoles()
  })

  it('returns 403 on GET /features without features:view', async () => {
    const cookie = await createRestrictedSession([])
    const res = await app.inject({
      method: 'GET',
      url: '/api/features',
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })

  it('returns 403 on POST /features without features:create', async () => {
    const cookie = await createRestrictedSession([
      { resource: 'features', action: 'view' },
    ])
    const res = await app.inject({
      method: 'POST',
      url: '/api/features',
      payload: { title: 'New' },
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })

  it('returns 403 on PATCH /features/:id without features:edit', async () => {
    const [item] = await testDb
      .insert(features)
      .values({ title: 'T' })
      .returning()
    const cookie = await createRestrictedSession([
      { resource: 'features', action: 'view' },
    ])
    const res = await app.inject({
      method: 'PATCH',
      url: `/api/features/${item.id}`,
      payload: { title: 'Updated' },
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })

  it('returns 403 on DELETE /features/:id without features:delete', async () => {
    const [item] = await testDb
      .insert(features)
      .values({ title: 'T' })
      .returning()
    const cookie = await createRestrictedSession([
      { resource: 'features', action: 'view' },
    ])
    const res = await app.inject({
      method: 'DELETE',
      url: `/api/features/${item.id}`,
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })
})
```

Assert `res.json().code` too when the route has more than one gate (`permission_denied` vs `subscription_required` / `feature_not_in_plan`) — the status alone cannot say which one answered.

The pattern for each test is: create a restricted session that has _just enough_ permission to reach the route (e.g. `view` only), then hit the route that requires the _next_ permission and assert 403. The `GET` test uses an empty grants list.

**Subscription-gated routes** (`requireSubscription`) run the subscription check first, so a restricted user without a subscription gets 403 from the gate and the test passes for the wrong reason. Call `await grantActiveSubscription(email)` in `createRestrictedSession`, and add a control test where the user holds the permission and gets 200 — `todos-routes.test.ts` is the reference.

### Implementation patterns

**Seed data via `testDb.insert` before tests that need it:**

```ts
it('returns the item when found', async () => {
  const [inserted] = await testDb
    .insert(features)
    .values({ title: 'My Feature' })
    .returning()

  const res = await app.inject({
    method: 'GET',
    url: `/api/features/${inserted.id}`,
  })
  expect(res.statusCode).toBe(200)
  expect(res.json().id).toBe(inserted.id)
})
```

**Verify unpatched fields remain unchanged:**

```ts
it('updates and returns the item', async () => {
  const [inserted] = await testDb
    .insert(features)
    .values({ title: 'Old', description: 'Keep' })
    .returning()

  const res = await app.inject({
    method: 'PATCH',
    url: `/api/features/${inserted.id}`,
    payload: { title: 'New' },
  })

  expect(res.statusCode).toBe(200)
  expect(res.json().title).toBe('New')
  expect(res.json().description).toBe('Keep')
})
```
