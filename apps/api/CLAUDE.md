# apps/api

Fastify + TypeScript — the REST API for this project.

## Stack

- **Framework**: Fastify v5 + `fastify-type-provider-zod` (validation and serialization via Zod)
- **ORM**: Drizzle ORM (pg dialect) — schema in code, migrations generated by drizzle-kit
- **Validation**: Zod (schemas declared in each module, shared between Fastify and TypeScript)
- **Auth**: better-auth (`auth.handler` integrated as a Fastify route — never use `toNodeHandler`)
- **Docs**: `@fastify/swagger` + `@scalar/fastify-api-reference` (available at `/docs`)
- **Tests**: Vitest + real test database (PostgreSQL)

## Environment variables

All variables are validated with Zod in `src/env.ts` at startup. If a required variable is missing or invalid, the process fails immediately with a clear message.

## Module structure

```
src/modules/<feature>/
├── <feature>-schema.ts   ← Zod schemas + inferred types
├── <feature>-service.ts  ← database operations (factory function)
└── <feature>-routes.ts   ← Fastify route registrations
```

The entry point is `src/app.ts`, which exports `buildApp(database: Database)`. Each route module is registered there via `app.register(featureRoutes, { database })`.

## Pagination and sorting

Every list endpoint must be paginated and sortable. The reusable utilities live in `src/lib/`:

| File                    | Exports                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `src/lib/pagination.ts` | `paginationQuerySchema`, `PaginationQuery`, `getPaginationParams`, `buildPaginatedResponse`, `paginatedResponseSchema` |
| `src/lib/sorting.ts`    | `sortingQuerySchema`, `SortingQuery`                                                                                   |

**`paginationQuerySchema`** — Zod schema for `page` (int ≥ 1, default 1) and `pageSize` (int 1–100, default 10). Used as `querystring` in list routes.

**`sortingQuerySchema(columns)`** — factory that takes a non-empty tuple of sortable column names (module-specific) and returns a Zod schema for `sortBy` (optional enum) and `sortOrder` (default `"asc"`). The column list is declared in the module's schema file so TypeScript enforces valid values end-to-end.

**`buildPaginatedResponse(data, total, pagination)`** — assembles `{ data, total, page, pageSize, totalPages }` from the service result and the parsed query. Call this in every list route handler instead of constructing the object manually.

**`paginatedResponseSchema(itemSchema)`** — generic Zod factory for the paginated response shape. Used once per module to declare the `200` response schema.

### How they compose in a module

The three layers each consume one piece:

```
schema file  →  declares sort columns, merges pagination + sorting into one query schema
service      →  receives the combined query, applies getPaginationParams + orderBy
route        →  uses the combined querystring schema, calls buildPaginatedResponse
```

See the `todos` module (`todos-schema.ts`, `todos-service.ts`, `todos-routes.ts`) as the canonical reference. The `audit` module is a read-only example (no POST/PATCH/DELETE) that also demonstrates the full pagination + sorting pattern.

### Non-paginated "all" endpoints

Occasionally a module needs to expose **all** records in a single array — for example, to populate a select field in another module (e.g. `GET /roles/all` populates the role selector in the Users form). Add a `/all` endpoint only when another module genuinely needs it for a UI select component. This endpoint returns a plain array (no pagination shape) and has no `page`/`pageSize`/`sortBy` params.

**Never** replace the main `GET /xxx` list endpoint with a non-paginated variant. The list endpoint is always paginated; the `/all` variant is an optional addition for select-field use cases.

## Filtering

Every list endpoint can optionally support field-level filtering via the reusable utilities in `src/lib/filtering.ts`. Add filtering to a module when the list screen needs a filter panel.

| File                    | Exports                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| `src/lib/filtering.ts`  | `filterQuerySchema`, `buildFilterWhereClause`, `FilterCondition`, `FilterLogic`, `FilterOperator` |

**`filterQuerySchema(allowedFields)`** — factory that accepts a non-empty tuple of filterable column names and returns a Zod schema with two fields:

- `filters` — accepts a JSON-encoded `FilterCondition[]` string; transforms to a typed array on validation; invalid JSON silently becomes `[]`
- `filterLogic` — `'AND' | 'OR'`, defaults to `'AND'`

Merge this into the module's `listQuerySchema` alongside pagination and sorting.

**`buildFilterWhereClause(conditions, logic, columnMap, coerce?)`** — builds a Drizzle `SQL | undefined` from the parsed filter conditions. Returns `undefined` when the list is empty (no `.where()` added). Pass the result to both the data query and the count query so pagination totals remain consistent.

The optional `coerce` map transforms raw filter values before Drizzle receives them. This is required for columns whose DB type differs from the serialized URL value — most commonly `timestamp` columns where the filter value arrives as an ISO string:

```ts
const FILTER_COERCE = {
  date: (v: unknown) => (typeof v === 'string' ? new Date(v) : v),
} as const
```

Without coercion, Drizzle will pass the raw string to PostgreSQL and the comparison will fail or error at runtime.

### Adding filtering to a module

#### 1. Schema (`<feature>-schema.ts`)

```ts
import { filterQuerySchema } from '@/lib/filtering'

export const FEATURE_FILTER_FIELDS = ['title', 'status', 'date'] as const
export type FeatureFilterField = (typeof FEATURE_FILTER_FIELDS)[number]

export const featuresFilterQuerySchema = filterQuerySchema([...FEATURE_FILTER_FIELDS])

// Merge into the existing list query schema
export const featuresListQuerySchema = paginationQuerySchema
  .merge(featuresSortingSchema)
  .merge(featuresFilterQuerySchema)
```

Only list fields that users will actually filter by. The field names must match the Drizzle column map keys in the service (see below) and the `FilterFieldDef.name` values on the frontend.

#### 2. Service (`<feature>-service.ts`)

```ts
import { buildFilterWhereClause } from '@/lib/filtering'

const FILTER_COLUMNS = {
  title: features.title,
  status: features.status,
  date: features.date,
} as const

// Only needed when a column type differs from the serialized URL value
const FILTER_COERCE = {
  date: (v: unknown) => (typeof v === 'string' ? new Date(v) : v),
} as const

async function list(query: FeaturesListQuery) {
  const { limit, offset } = getPaginationParams(query.page, query.pageSize)
  const sortCol = SORT_COLUMNS[query.sortBy ?? 'createdAt']
  const sortFn = query.sortOrder === 'desc' ? desc : asc
  const where = buildFilterWhereClause(
    query.filters,
    query.filterLogic,
    FILTER_COLUMNS,
    FILTER_COERCE
  )

  const [data, [{ total }]] = await Promise.all([
    database.select().from(features).where(where).orderBy(sortFn(sortCol)).limit(limit).offset(offset),
    database.select({ total: count() }).from(features).where(where),
  ])
  return { data, total }
}
```

Always pass `where` to both queries — the count query drives pagination totals.

#### 3. Tests (`<feature>-routes.test.ts`)

Add a `describe('Filtering')` block inside `describe('GET /features')`:

| Test | What to verify |
|------|----------------|
| `filters` with `eq` on an enum field (e.g. `status=pending`) | returns only matching records |
| `filters` with `contains` on a text field | case-insensitive match |
| `filters` with `gte` on a date/number field | range boundary respected |
| two conditions with `AND` logic | returns intersection |
| two conditions with `OR` logic | returns union |
| `filters=[]` (empty array) | returns all records |
| `filters=invalid-json` | returns all records (silent fallback) |

Seed the data via `testDb.insert` before each test case. Pass `filters` as a JSON-encoded string in the query string: `filters=JSON.stringify([{ field: 'status', op: 'eq', value: 'pending' }])`.

See `apps/api/src/modules/todos/todos-routes.test.ts` for the reference implementation.

## File uploads

The file upload system is implemented as a standalone `uploads` module. Any other module can allow users to attach files by adding a junction table and a few lines to its service. See `src/modules/uploads/CLAUDE.md` for the full reference.

### Infrastructure (`src/lib/`)

| File | Purpose |
|------|---------|
| `src/lib/storage/types.ts` | `StorageProvider` interface (`save`, `delete`, `getUrl`) |
| `src/lib/storage/local-storage.ts` | `LocalStorageProvider` — writes to `UPLOAD_DIR`, serves via `/files/*` |
| `src/lib/storage/index.ts` | `createStorageProvider(env)` factory — returns local or throws for S3 (stub) |
| `src/lib/image-processor.ts` | `processImage(buffer, mimeType)` — generates 4 WebP variants via `sharp` |

The provider instance is created once in `app.ts` and injected into every module that needs it via route options. Files are served publicly at `/files/*` via `@fastify/static` — no auth required on that path (needed for `<img>` tags).

### Environment variables

| Variable | Default | Notes |
|----------|---------|-------|
| `STORAGE_PROVIDER` | `'local'` | `'s3'` stub exists but throws |
| `UPLOAD_DIR` | `'./storage'` | Local storage root directory |
| `UPLOAD_MAX_SIZE_MB` | `50` | Enforced in `POST /uploads` |
| `UPLOAD_BASE_URL` | `'http://localhost:3333'` | Prepended to storage keys to build public URLs |

### Adding file attachments to a module

Use `todos` as the reference implementation.

1. Create a junction table `xxx_attachments(xxx_id FK cascade, upload_id FK cascade)`
2. Add `attachments: uploadSchema.array()` to the response schema and `attachmentIds: z.array(z.string()).optional().default([])` to create/update schemas
3. In the service: JOIN with `uploads` on reads; sync `xxx_attachments` rows on create/update; on delete, fetch upload IDs → delete the record (cascades junction rows) → delete upload DB rows → delete storage keys (best-effort)
4. Accept `storage: StorageProvider` in route options and pass it through to the service factory

## PDF export

Modules can expose a `GET /xxx/export` endpoint that streams a PDF report to the client. The rendering happens server-side via `@react-pdf/renderer`. See `src/lib/pdf/CLAUDE.md` for the rendering infrastructure (templates, `BaseDocument`, colors, styles).

Use `todos` as the reference implementation (`todos-schema.ts`, `todos-service.ts`, `todos-routes.ts`, `src/modules/todos/templates/todos-report.tsx`).

### When to add PDF export

Add a PDF export endpoint when the module has a list screen with filters and the user needs to take that data offline. It always mirrors the list endpoint's sort/filter params — minus pagination.

### Adding PDF export to a module

#### 1. Schema (`<feature>-schema.ts`)

The export query reuses the existing sorting and filter schemas, with no pagination:

```ts
export const featuresExportQuerySchema = featuresSortingSchema.merge(featuresFilterQuerySchema)
export type FeaturesExportQuery = z.infer<typeof featuresExportQuerySchema>
```

#### 2. Template (`src/modules/<feature>/templates/<feature>-report.tsx`)

See `src/lib/pdf/CLAUDE.md` for the full template guide. The exported function signature must be:

```ts
export async function renderFeatureReport(items: FeatureRow[]): Promise<Buffer>
```

#### 3. Service (`<feature>-service.ts`)

Add `generateReport` to the factory. Always cap with `.limit(5000)` — an unbounded export is a DoS vector. Load the template via dynamic `import()` so the PDF runtime is only initialised when the route is actually called:

```ts
async function generateReport(query: FeaturesExportQuery): Promise<Buffer> {
  const sortCol = SORT_COLUMNS[query.sortBy ?? 'createdAt']
  const sortFn = query.sortOrder === 'desc' ? desc : asc
  const where = buildFilterWhereClause(
    query.filters,
    query.filterLogic,
    FILTER_COLUMNS,
    FILTER_COERCE,
  )

  const data = await database
    .select()
    .from(features)
    .where(where)
    .orderBy(sortFn(sortCol))
    .limit(5000)

  const { renderFeatureReport } = await import('./templates/feature-report')
  return renderFeatureReport(data)
}

return { list, getById, create, update, remove, generateReport }
```

#### 4. Route (`<feature>-routes.ts`)

The export endpoint uses the same `view` permission as the list. Wrap `generateReport` in a try/catch — render failures must return a clean 500, not leak a stack trace. Audit after success with a minimal metadata object (never the raw query params — `filters` can contain arbitrary user data):

```ts
app.get(
  '/features/export',
  {
    schema: {
      tags: ['features'],
      description: 'Export features as PDF',
      querystring: featuresExportQuerySchema,
    },
    preHandler: requirePermission('features', 'view'),
  },
  async (request, reply) => {
    let buffer: Buffer
    try {
      buffer = await service.generateReport(request.query)
    } catch {
      return reply.status(500).send({ message: 'Failed to generate report' })
    }
    const date = new Date().toISOString().split('T')[0]
    await request.audit('export', 'features', undefined, {
      sortBy: request.query.sortBy,
      sortOrder: request.query.sortOrder,
      filterLogic: request.query.filterLogic,
      filterCount: request.query.filters?.length ?? 0,
    })
    return reply
      .header('Content-Type', 'application/pdf')
      .header('Content-Disposition', `attachment; filename="features-${date}.pdf"`)
      .send(buffer)
  },
)
```

> **Note**: `'export'` must be present in the `action` union in `src/modules/audit/audit-service.ts` and `src/types.ts`. It is already registered — no change needed for new modules.

> **Note**: Binary responses cannot carry a Zod `response` schema with `fastify-type-provider-zod`. Omitting `response` from the schema is intentional and correct for this endpoint type.

## Creating a new module (CRUD)

Use the `todos` module as the reference implementation. Follow this order exactly.

### 0. Register the resource (`src/config/permissions.ts`)

Every module that exposes user-facing data must declare its resource and actions here. This is the single source of truth for what permissions exist — bootstrap, test helpers, and the `GET /permissions/resources` endpoint all read from it.

```ts
// src/config/permissions.ts
{
  resource: "features",
  label: "Features",
  actions: ["view", "create", "edit", "delete"],
},
```

`PermissionAction = "view" | "create" | "edit" | "delete"` is the full set of supported actions. TypeScript enforces this via `satisfies` — adding an unsupported action is a compile error. If the module genuinely needs a new action type, extend `PermissionAction` first.

### 1. Schema (`<feature>-schema.ts`)

Declare all Zod schemas for the module. The main schema (`featureSchema`) describes the object returned by the API. The others describe request bodies and the paginated list:

```ts
import z from 'zod'
import {
  paginatedResponseSchema,
  paginationQuerySchema,
} from '@/lib/pagination'
import { sortingQuerySchema } from '@/lib/sorting'

export const featureSchema = z
  .object({
    id: z.string(),
    title: z.string(),
    // ...other fields
    createdAt: z.date(),
    updatedAt: z.date(),
  })
  .meta({ id: 'Feature', title: 'Feature' })

export const createFeatureSchema = z.object({
  title: z.string().min(1).max(200),
  // ...mutable fields — always add .max() to mirror the frontend constraint
})

export const updateFeatureSchema = z.object({
  title: z.string().min(1).max(200).optional(),
  // ...optional fields
})

export type CreateFeatureInput = z.infer<typeof createFeatureSchema>
export type UpdateFeatureInput = z.infer<typeof updateFeatureSchema>

// Pagination + sorting for the list endpoint
export const FEATURE_SORT_COLUMNS = ['title', 'createdAt'] as const
export type FeatureSortColumn = (typeof FEATURE_SORT_COLUMNS)[number]

export const featuresSortingSchema = sortingQuerySchema([
  ...FEATURE_SORT_COLUMNS,
])
export const featuresListQuerySchema = paginationQuerySchema.merge(
  featuresSortingSchema
)
export type FeaturesListQuery = z.infer<typeof featuresListQuerySchema>

export const paginatedFeaturesSchema = paginatedResponseSchema(
  featureSchema
).meta({
  id: 'PaginatedFeatures',
  title: 'PaginatedFeatures',
})
export type PaginatedFeatures = z.infer<typeof paginatedFeaturesSchema>
```

Choose `FEATURE_SORT_COLUMNS` based on the fields users are likely to sort by. Always include `createdAt` as a fallback — it is the default sort column when `sortBy` is absent.

**Always add `.meta({ id, title })` to the main entity schema.** This registers it in Zod's global registry so `@fastify/swagger` emits it as a named `$ref` component (`components/schemas/Feature`) instead of inlining the object schema in every response. Without it, kubb generates duplicate inline types per endpoint and hits a naming collision when the schema contains an enum field, producing a broken array type (e.g. `Feature[] → StatusEnum[]`).

### 2. Database schema (`src/db/schema/<feature>.ts`)

Declare the table with Drizzle. Add the export to `src/db/schema/index.ts`:

```ts
import { pgTable, text, timestamp } from 'drizzle-orm/pg-core'
import { uuidv7 } from 'uuidv7'

export const features = pgTable('features', {
  id: text('id')
    .primaryKey()
    .$defaultFn(() => uuidv7()),
  title: text('title').notNull(),
  createdAt: timestamp('created_at').notNull().defaultNow(),
  updatedAt: timestamp('updated_at')
    .notNull()
    .defaultNow()
    .$onUpdateFn(() => new Date()),
})
```

After creating the schema, generate and apply the migration:

```bash
pnpm db:generate
pnpm db:migrate
pnpm db:migrate:test
```

### 3. Service (`<feature>-service.ts`)

A factory function that receives `database: Database` and returns the data access methods. No business logic beyond SQL — any logic that is not plain SQL must be extracted and tested separately.

`list()` always accepts `FeaturesListQuery` and applies both pagination and ordering. The `SORT_COLUMNS` map translates the string column name (from the query param) to the actual Drizzle column reference. The default sort column is used when `sortBy` is absent.

```ts
import { asc, count, desc, eq } from 'drizzle-orm'
import type { Database } from '@/db'
import { features } from '@/db/schema'
import { getPaginationParams } from '@/lib/pagination'
import type {
  CreateFeatureInput,
  FeaturesListQuery,
  UpdateFeatureInput,
} from './feature-schema'

const SORT_COLUMNS = {
  title: features.title,
  createdAt: features.createdAt,
} as const

export function createFeatureService(database: Database) {
  async function list(query: FeaturesListQuery) {
    const { limit, offset } = getPaginationParams(query.page, query.pageSize)
    const sortCol = SORT_COLUMNS[query.sortBy ?? 'createdAt']
    const sortFn = query.sortOrder === 'desc' ? desc : asc
    const [data, [{ total }]] = await Promise.all([
      database
        .select()
        .from(features)
        .orderBy(sortFn(sortCol))
        .limit(limit)
        .offset(offset),
      database.select({ total: count() }).from(features),
    ])
    return { data, total }
  }

  async function getById(id: string) {
    const [item] = await database
      .select()
      .from(features)
      .where(eq(features.id, id))
    return item ?? null
  }

  async function create(data: CreateFeatureInput) {
    const [item] = await database.insert(features).values(data).returning()
    return item
  }

  async function update(id: string, data: UpdateFeatureInput) {
    const [item] = await database
      .update(features)
      .set(data)
      .where(eq(features.id, id))
      .returning()
    return item ?? null
  }

  async function remove(id: string) {
    await database.delete(features).where(eq(features.id, id))
  }

  return { list, getById, create, update, remove }
}

export type FeatureService = ReturnType<typeof createFeatureService>
```

### 4. Routes (`<feature>-routes.ts`)

A Fastify plugin that receives `{ database, requirePermission, auditService }` as options. Every route must have a `schema` with `tags`, `description`, and the Zod schemas for body/params/response, **plus** a `preHandler` that enforces the matching permission:

| Route                  | Permission        |
| ---------------------- | ----------------- |
| `GET /features`        | `features:view`   |
| `GET /features/:id`    | `features:view`   |
| `POST /features`       | `features:create` |
| `PATCH /features/:id`  | `features:edit`   |
| `DELETE /features/:id` | `features:delete` |

Every mutation handler (POST, PATCH, DELETE) must call `request.audit()` after the service call succeeds. `request.audit` is injected by `registerAuditRequest` (registered once in the authenticated scope in `app.ts`) — route modules do **not** need to receive or import `auditService`. Do not call `request.audit()` on read-only routes (`GET`).

The method signature is:

```ts
request.audit(action, resource, resourceId?, metadata?)
```

- `action` — `"create"`, `"edit"`, or `"delete"`
- `resource` — the resource string from `src/config/permissions.ts`
- `resourceId` — the id of the affected record (omit or pass `undefined` if not applicable)
- `metadata` — pass `request.body` for create/edit; omit for delete (no body)

Failures are caught and logged server-side automatically — never call `.catch()` yourself.

```ts
import z from 'zod'
import type { FastifyTypedInstance, RequirePermission } from '../../types'
import type { Database } from '../../db'
import {
  featureSchema,
  createFeatureSchema,
  updateFeatureSchema,
  featuresListQuerySchema,
  paginatedFeaturesSchema,
} from './feature-schema'
import { createFeatureService } from './feature-service'
import { buildPaginatedResponse } from '@/lib/pagination'

export async function featureRoutes(
  app: FastifyTypedInstance,
  {
    database,
    requirePermission,
  }: { database: Database; requirePermission: RequirePermission }
) {
  const service = createFeatureService(database)

  app.get(
    '/features',
    {
      schema: {
        tags: ['features'],
        description: 'List features',
        querystring: featuresListQuerySchema,
        response: { 200: paginatedFeaturesSchema },
      },
      preHandler: requirePermission('features', 'view'),
    },
    async (request) => {
      const { data, total } = await service.list(request.query)
      return buildPaginatedResponse(data, total, request.query)
    }
  )

  app.get(
    '/features/:id',
    {
      schema: {
        tags: ['features'],
        description: 'Get a feature by id',
        params: z.object({ id: z.string() }),
        response: {
          200: featureSchema,
          404: z.object({ message: z.string() }),
        },
      },
      preHandler: requirePermission('features', 'view'),
    },
    async (request, reply) => {
      const item = await service.getById(request.params.id)
      if (!item) return reply.status(404).send({ message: 'Feature not found' })
      return item
    }
  )

  app.post(
    '/features',
    {
      schema: {
        tags: ['features'],
        description: 'Create a feature',
        body: createFeatureSchema,
        response: { 201: featureSchema },
      },
      preHandler: requirePermission('features', 'create'),
    },
    async (request, reply) => {
      const item = await service.create(request.body)
      await request.audit('create', 'features', item.id, request.body)
      return reply.status(201).send(item)
    }
  )

  app.patch(
    '/features/:id',
    {
      schema: {
        tags: ['features'],
        description: 'Update a feature',
        params: z.object({ id: z.string() }),
        body: updateFeatureSchema,
        response: {
          200: featureSchema,
          404: z.object({ message: z.string() }),
        },
      },
      preHandler: requirePermission('features', 'edit'),
    },
    async (request, reply) => {
      const item = await service.update(request.params.id, request.body)
      if (!item) return reply.status(404).send({ message: 'Feature not found' })
      await request.audit('edit', 'features', request.params.id, request.body)
      return item
    }
  )

  app.delete(
    '/features/:id',
    {
      schema: {
        tags: ['features'],
        description: 'Delete a feature',
        params: z.object({ id: z.string() }),
        response: { 204: z.null().describe('Feature deleted') },
      },
      preHandler: requirePermission('features', 'delete'),
    },
    async (request, reply) => {
      await service.remove(request.params.id)
      await request.audit('delete', 'features', request.params.id)
      return reply.status(204).send(null)
    }
  )
}
```

**Key rule**: the `request.audit()` call must come **after** the service call succeeds. For handlers with an early 404 return, place it after the guard so it only fires on the success path.

### 5. Register in `app.ts`

All modules that require authentication must be registered inside the `authenticated` scope. `requirePermission` is passed to every module; `request.audit` is available automatically via `registerAuditRequest` — route modules do not need to receive `auditService`.

```ts
import { featureRoutes } from './modules/feature/feature-routes'
import { createRequirePermission } from './hooks/require-permission'
import { createAuditService } from './modules/audit/audit-service'
import { registerAuditRequest } from './hooks/audit-request'

// inside the authenticated scope in buildApp:
app.register(async (authenticated) => {
  authenticated.addHook('preHandler', createRequireAuth(auth))

  const requirePermission = createRequirePermission(database)
  registerAuditRequest(authenticated, createAuditService(database))

  authenticated.register(todosRoutes, { database, requirePermission })
  authenticated.register(featureRoutes, { database, requirePermission }) // ← add here
})
```

Registering at the root instead of inside `authenticated` will leave the routes publicly accessible.

## Testing

**Commands:**

```bash
pnpm test          # single run
pnpm test:watch    # watch mode
```

### Philosophy

Backend tests are route integration tests: they exercise the full Fastify stack (validation, serialization, routing) against a real test database. This ensures the entire stack works — Zod schema, Drizzle, database constraints — without any abstraction in the middle.

### What NOT to do

- **Do not mock the database.** Replacing the database with a mock eliminates exactly what makes these tests valuable: verifying that the SQL is correct, that constraints are respected, and that Drizzle behaves as expected.
- **Do not test the service directly when it has no logic of its own.** The `todos` service, for example, is pure SQL delegated to Drizzle — testing `createTodosService` in isolation would only re-assert that `.insert().returning()` works, which is not this project's responsibility. These cases are already covered by route tests.
- **Do not write E2E tests here.** Playwright E2E tests live in `apps/web/e2e/` and cover full CRUD flows against the real backend. Do not duplicate that level here.

### Test infrastructure

The helpers in `src/test/helpers.ts` provide:

- `testDb` — Drizzle instance pointing to the `api_test` database (port 5436)
- `createTestApp()` — creates an app instance with `testDb` injected
- `cleanupXxx()` — truncates a table between tests
- `cleanupAuth()` — truncates all auth tables (session, account, verification, user)
- `createTestSession(app)` — signs up a test user assigned to the `__test_admin__` role (all permissions); returns the session cookie string
- `createRoleWithPermissions(grants)` — creates a fresh role with exactly the given permissions; used for permission enforcement tests

When adding a new module, add a `cleanupFeature()` function to `helpers.ts`:

```ts
import { features } from '@/db/schema/feature'

export async function cleanupFeature() {
  await testDb.delete(features)
}
```

### Test file structure (`<feature>-routes.test.ts`)

Since all modules live inside the authenticated scope, every route test file must:

1. Create a session in `beforeAll` and clean up auth in `afterAll`
2. Pass the session cookie on every authenticated request
3. Include one top-level 401 test (outside any `describe`) to verify the module is inside the authenticated scope

```ts
import { describe, it, expect, beforeAll, beforeEach, afterAll } from 'vitest'
import {
  createTestApp,
  cleanupFeature,
  cleanupAuth,
  createTestSession,
  testDb,
} from '@/test/helpers'
import { features } from '@/db/schema/feature'

const app = createTestApp()
let authCookie = ''

beforeAll(async () => {
  await cleanupAuth()
  authCookie = await createTestSession(app)
})

beforeEach(async () => {
  await cleanupFeature()
})

afterAll(async () => {
  await cleanupAuth()
  await app.close()
})

it('returns 401 on any route when not authenticated', async () => {
  const res = await app.inject({ method: 'GET', url: '/features' })
  expect(res.statusCode).toBe(401)
})
```

### Required coverage per endpoint

| Endpoint               | Required cases                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /features`        | empty list returns `{ data: [], total: 0, page: 1, pageSize: 10, totalPages: 0 }`; list with items; `page`/`pageSize` applied correctly (correct slice returned); `sortBy`/`sortOrder` applied (items in expected order) |
| `GET /features/:id`    | 404 for unknown id; returns correct item                                                                                                                                                                                 |
| `POST /features`       | 201 with correct body; 400 for invalid body                                                                                                                                                                              |
| `PATCH /features/:id`  | 404 for unknown id; updates and returns correct fields (fields not sent remain unchanged)                                                                                                                                |
| `DELETE /features/:id` | 204 for existing item; 204 for unknown id                                                                                                                                                                                |

### Permission enforcement tests

Every route module must include a `describe("Permission enforcement")` block that verifies each route returns 403 when the session user's role lacks the required permission. Use `createRoleWithPermissions` to build a restricted session:

```ts
import { eq } from 'drizzle-orm'
import {
  createRoleWithPermissions,
  cleanupUsers,
  cleanupRoles,
} from '@/test/helpers'
import { user } from '@/db/schema/authentication'

describe('Permission enforcement', () => {
  async function createRestrictedSession(
    grants: { resource: string; action: string }[]
  ) {
    const role = await createRoleWithPermissions(grants)
    const email = `restricted-features-${Date.now()}@test.com`
    const res = await app.inject({
      method: 'POST',
      url: '/api/auth/sign-up/email',
      payload: JSON.stringify({
        email,
        name: 'Restricted',
        password: 'Password123!',
      }),
      headers: { 'content-type': 'application/json' },
    })
    await testDb
      .update(user)
      .set({ roleId: role.id })
      .where(eq(user.email, email))
    const setCookie = res.headers['set-cookie']
    const cookies = Array.isArray(setCookie) ? setCookie : [setCookie ?? '']
    return cookies.map((c) => c.split(';')[0]).join('; ')
  }

  beforeEach(async () => {
    await cleanupUsers()
    await cleanupRoles()
  })

  it('returns 403 on GET /features without features:view', async () => {
    const cookie = await createRestrictedSession([])
    const res = await app.inject({
      method: 'GET',
      url: '/features',
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })

  it('returns 403 on POST /features without features:create', async () => {
    const cookie = await createRestrictedSession([
      { resource: 'features', action: 'view' },
    ])
    const res = await app.inject({
      method: 'POST',
      url: '/features',
      payload: { title: 'New' },
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })

  it('returns 403 on PATCH /features/:id without features:edit', async () => {
    const [item] = await testDb
      .insert(features)
      .values({ title: 'T' })
      .returning()
    const cookie = await createRestrictedSession([
      { resource: 'features', action: 'view' },
    ])
    const res = await app.inject({
      method: 'PATCH',
      url: `/features/${item.id}`,
      payload: { title: 'Updated' },
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })

  it('returns 403 on DELETE /features/:id without features:delete', async () => {
    const [item] = await testDb
      .insert(features)
      .values({ title: 'T' })
      .returning()
    const cookie = await createRestrictedSession([
      { resource: 'features', action: 'view' },
    ])
    const res = await app.inject({
      method: 'DELETE',
      url: `/features/${item.id}`,
      headers: { cookie },
    })
    expect(res.statusCode).toBe(403)
  })
})
```

The pattern for each test is: create a restricted session that has _just enough_ permission to reach the route (e.g. `view` only), then hit the route that requires the _next_ permission and assert 403. The `GET` test uses an empty grants list.

### Implementation patterns

**Seed data via `testDb.insert` before tests that need it:**

```ts
it('returns the item when found', async () => {
  const [inserted] = await testDb
    .insert(features)
    .values({ title: 'My Feature' })
    .returning()

  const res = await app.inject({
    method: 'GET',
    url: `/features/${inserted.id}`,
  })
  expect(res.statusCode).toBe(200)
  expect(res.json().id).toBe(inserted.id)
})
```

**Verify unpatched fields remain unchanged:**

```ts
it('updates and returns the item', async () => {
  const [inserted] = await testDb
    .insert(features)
    .values({ title: 'Old', description: 'Keep' })
    .returning()

  const res = await app.inject({
    method: 'PATCH',
    url: `/features/${inserted.id}`,
    payload: { title: 'New' },
  })

  expect(res.statusCode).toBe(200)
  expect(res.json().title).toBe('New')
  expect(res.json().description).toBe('Keep')
})
```
